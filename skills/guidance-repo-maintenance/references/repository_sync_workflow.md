# 정본 저장소·로컬·Codex 설치본 동기화 절차

## 1. 적용 조건과 동기화 방향

사용자가 `지침 저장소 동기화 확인`, `GitHub 지침 반영`, `원격·로컬 싱크`, `앱에 스킬 반영`, `동기화 후 PR`처럼 원격 정본·로컬 원본·설치본 사이의 동기화를 요청하면 적용한다. 단순 저장소 상태 확인에는 기계적으로 적용하지 않는다. 먼저 요청의 방향을 구분한다.

- 내려받기: `현재 정본 저장소의 기본 브랜치 → 로컬 지침 원본 → Codex 설치본 → 앱 인식`
- 올리기: `로컬 지침 원본의 확정 변경 → 현재 정본 저장소 기능 브랜치·커밋·PR`
- 양방향: 원격 기준선을 먼저 확인하고 로컬 변경을 병합한 뒤, 확정 파일만 PR로 올리고 설치본을 검증한다.

GitHub 변경, 로컬 작업본, 사용자 스킬 설치본, 현재 열린 Codex 작업의 인식 상태는 서로 다른 단계다. 한 단계의 성공을 다음 단계의 성공으로 표현하지 않는다.

이 starter를 복제한 뒤에는 복제한 사용자의 저장소가 정본이다. 원본 제공자의 `m1`은 자동 동기화 대상이 아니며, 필요한 개선을 별도로 선택해 가져오는 경우에만 사용자가 명시한 범위에서 대조한다.

## 2. 사전 점검

1. 현재 폴더가 지침 원본 저장소인지 확인하고 작업 트리의 기존 변경을 목록화한다.
2. 현재 PC와 조직 정책에서 허용되는 GitHub 접근 방식을 확인한다. 환경이 불명확하면 더 제한적인 규칙을 우선한다.
3. 조직의 제한 PC에서는 허용된 GitHub 플러그인 또는 MCP 등 승인된 경로로만 원격을 읽고 수정한다. 승인되지 않은 SSH, PAT, GCM, 로컬 `fetch`·`pull`·`push` 또는 우회 접속을 시도하지 않는다.
4. 제한 PC에서 허용된 원격 접근 수단을 사용할 수 없으면 원격을 확인·반영하지 못한 상태로 보고하고 중단한다. 다른 네트워크 경로나 인증 방식으로 임의 전환하지 않는다.
5. 전송 후보를 파일 단위로 확정한다. 사건자료, 개인정보, 내부 문서번호, 비공개 참조본, 인증정보, 런타임, 로그, OCR·변환 결과와 생성 산출물은 제외한다.
6. 현재 정본 저장소의 기본 브랜치(초기값은 보통 `main`) 최신 커밋 SHA와 재귀 파일 트리를 확인한다. PR을 만들 때까지 기준 SHA가 바뀌면 비교부터 다시 한다.

## 3. 원격과 로컬 대조

원격 blob SHA와 로컬 파일의 Git blob SHA 또는 내용을 비교한다. 동일 바이트 복사를 검증할 때는 `git hash-object --no-filters -- <경로>`로 원시 바이트를 해시할 수 있다. 다만 `core.autocrlf`, `.gitattributes`, clean 필터가 적용되는 작업 트리는 원격 blob과 원시 로컬 SHA가 달라질 수 있으므로, 적용 중인 변환을 반영한 내용도 함께 비교하고 줄바꿈·필터 차이만으로 충돌로 분류하지 않는다. 전체 경로나 파일 내용을 한꺼번에 화면에 출력하지 말고 여러 묶음으로 처리하며, 한 묶음은 기본 40~60개 이하로 둔다. 사용자에게는 총계와 불일치 파일만 보여 준다.

각 파일을 다음 상태로 분류한다.

| 상태 | 처리 |
|---|---|
| 동일 | 변경하지 않는다. |
| 원격 신규·로컬 누락 | 원격 파일을 추가한다. |
| 원격 변경·로컬 고유 변경 없음 | 원격 내용을 반영한다. |
| 로컬 고유 변경·원격 변경 없음 | 로컬 변경을 보존하고 PR 후보 여부를 별도로 판단한다. |
| 양쪽 변경 또는 기준 불명확 | 기계적으로 덮어쓰지 않고 의미 단위로 병합한다. |
| 비공유·제외 대상 | 동기화와 PR 대상에서 제외하고 필요하면 사유만 보고한다. |

로컬 이력과 원격 이력이 직접 연결되지 않았거나 이전 기준 SHA가 불명확하면 `ahead/behind`를 추정하지 않는다. 현재 원격 SHA, 파일별 해시, 실제 내용을 기준으로 판정하고 의도적 불일치는 이유와 함께 남긴다.

## 4. 로컬 반영과 중단 복구

1. 누락 파일, 안전하게 교체 가능한 파일, 병합이 필요한 파일 순서로 반영한다.
2. 사용자 또는 다른 작업자가 만든 기존 변경을 되돌리지 않는다.
3. 한 번에 긴 패치나 대량 출력을 실행하지 않는다. 큰 파일과 많은 파일은 작은 묶음으로 처리하고 결과는 개수 중심으로 요약한다.
4. 앱, 작업 또는 도구 실행이 중단되면 직전 명령을 곧바로 반복하지 않는다. 현재 파일 상태와 원격 기준 SHA를 다시 확인하고 남은 누락·불일치만 이어서 처리한다.
5. 오래 실행되면서 진행 표시가 없는 작업은 결과 파일과 프로세스 상태를 확인한 뒤 중단 또는 더 작은 단위로 재실행한다.

## 5. 검증과 완료 판정

로컬 원본 반영은 다음을 모두 확인해야 완료로 본다.

1. 원격 재귀 트리의 로컬 누락 파일이 0개다.
2. 원격과 동일해야 하는 파일은 blob SHA가 일치하거나, 적용 중인 줄바꿈·clean 필터를 반영한 내용 비교에서 일치한다.
3. 의도적 불일치 파일은 경로와 보존 이유가 정리되어 있다.
4. 변경 파일에 민감정보와 제외 대상이 없다.
5. 수정한 스킬은 현재 환경에 공식 skill validator가 제공되면 `skill-creator`의 `quick_validate.py` 또는 동등한 validator로 검사한다. 공식 validator를 사용할 수 없으면 `SKILL.md`의 필수 frontmatter와 참조 경로 등 최소 구조를 점검하고, validator 미실행 사실을 최종 보고에 남긴다.
6. 관련 스크립트가 있으면 문법 검사나 합리적인 최소 테스트를 수행한다.

검증 도구의 전체 출력을 반복해서 노출하지 말고 `전체 / 일치 / 누락 / 의도적 불일치 / 오류` 집계와 필요한 경로만 보고한다.

## 6. Codex 설치본과 앱 인식

스킬 원본이 바뀌었으면 저장소 루트에서 다음 순서로 설치본을 갱신한다.

1. `powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\sync_codex_skills.ps1 -DryRun`
2. `powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\sync_codex_skills.ps1`
3. `powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\sync_codex_skills.ps1 -VerifyOnly`

실제 복사와 SHA-256 검증이 성공해야 설치본 동기화가 완료된다. 파일 일치와 현재 열린 작업의 스킬 목록 갱신은 구분한다. Codex가 새 스킬이나 변경 내용을 현재 작업에서 인식하지 못하면 새 작업에서 먼저 확인하고, 계속 보이지 않을 때 앱을 재시작한다.

## 7. 기능 브랜치·커밋·PR

1. 최신 정본 저장소 기본 브랜치 SHA에서 기능 브랜치를 만든다. 저장소에 별도 브랜치 명명 규칙이 있으면 그 규칙을 우선한다.
2. 확정한 파일만 명시적으로 선택해 커밋한다. 더러운 로컬 작업 트리 전체를 브랜치에 복제하지 않는다.
3. 일반 커밋 메시지와 PR 제목은 한국어를 기본으로 한다.
4. PR을 열기 전에 기준 SHA, 변경 파일 목록, diff, 개인정보·인증정보·런타임 포함 여부를 다시 확인한다.
5. PR 생성 후 base/head, 변경 파일 수와 실제 diff를 확인한다. 원격 기본 브랜치는 직접 수정하지 않는다.
6. PR 생성·검증과 기본 브랜치 병합은 별도 상태다. 병합 전에는 `PR 생성(미병합)`으로 보고하고, 병합 후 기본 브랜치의 최신 SHA와 트리에 실제 반영된 것을 다시 확인한 뒤에만 `기본 브랜치 반영 완료`로 보고한다. 병합 뒤 로컬 원본·설치본 갱신이 요청 범위에 포함되면 그 단계도 별도로 다시 수행한다.

## 8. 최종 보고

최종 보고에는 다음을 구분해 적는다.

- 확인한 원격 최신 커밋 SHA
- 로컬 대조 결과: 전체, 일치, 누락, 의도적 불일치
- 실제로 반영하거나 PR에 포함한 파일
- `PR 생성(미병합)` 또는 `기본 브랜치 반영(병합 확인)` 상태
- 스킬 validator, 스크립트 테스트, 설치본 SHA 검증 결과
- 앱 인식 확인 여부와 새 작업·재시작 필요 여부
- 중단되었거나 검증하지 못한 항목

`동기화 완료`는 요청 범위의 단계가 모두 끝났을 때만 사용한다. 예를 들어 로컬 파일만 반영하고 설치본 검증을 하지 않았다면 `로컬 원본 반영 완료, 설치본 미검증`으로, PR만 열려 있다면 `PR 생성 완료, 기본 브랜치 미병합`으로 보고한다.
