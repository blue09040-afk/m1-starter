# 비식별 Markdown 샘플 등재 표준

## 1. 목적과 적용 범위

권익위 고충민원, 공익신고 등 반복 업무의 확정 문서에서 재사용 가능한 구조와 문체를 추출해 `m1`의 Markdown 샘플로 등재할 때 적용한다. 실제 사건 원본이나 자동 마스킹 결과를 공유하는 절차가 아니다.

## 2. 샘플 유형

| 유형 | 용도 | 포함 범위 |
|---|---|---|
| 구조 예시 | 필드, 문단 순서, 필수·선택 항목과 붙임 구조 안내 | 중립적인 자리표시자와 짧은 설명 |
| 문안 예시 | Chat이 완성형 초안의 문체·문장 연결을 참고 | 완전히 가상화한 사실관계와 비식별 완성 문안 |

구조 예시와 문안 예시를 한 파일에 혼합하지 않는다. 실제 확정본은 어느 유형에도 포함하지 않는다.

## 3. 후보 선정 게이트

1. 사용자가 결재·발송 확정을 명시한 문서만 후보로 삼는다. 사용자가 제공 문서를 재사용 샘플에 반영하도록 명시적으로 요청한 경우에도, 문서 자체에서 시행·결재 완료 등 확정 상태가 확인되거나 사용자가 그 확정 상태를 확인한 경우에 한한다.
2. 원본은 사건 폴더의 비공유 참조본으로 보존하고 GitHub, Chat 프로젝트 소스, 공유 ZIP에 넣지 않는다.
3. 같은 업무의 현재 샘플과 구조가 실질적으로 다르거나, 반복 오류를 줄이는 문체상 이점이 있을 때만 신규·교체 후보로 삼는다.
4. 단일 사건의 특이 사실, 특정 부서 관행, 일회성 법률판단은 공통 샘플로 승격하지 않는다.

## 4. 작성 절차

1. 원본과 분리된 새 Markdown에서 문단·필드·붙임 구조만 옮긴다.
2. **실무 공문 초안의 기본 골격으로 사용하는 구조 예시는** 확정본의 번호체계, 문단 순서, 표제와 붙임 흐름을 실무 사용 순서대로 보존한다. 이를 `관련문서`, `처리결과`, `후속조치` 같은 추상 필드 목록으로 다시 설계하여 실제 확정 문서의 골격을 바꾸지 않는다.
3. 실제 사건번호, 민원·신고 제목, 주소·지번, 업체·시설명, 판결·처분정보, 부서·직원명, 문서번호·날짜·기한, 연락처, 결재·시행정보를 제거한다.
4. 신고자와 피신고자의 관계, 내부자만 아는 경위, 제보 경로처럼 신고자를 추정하게 하는 간접 식별정보도 제거하거나 일반화한다.
5. 구조 예시는 `20XX`, `0000`, `ㅇㅇ`, `[확인 필요]` 또는 의미가 분명한 중립 자리표시자(예: `<민원번호>`)를 사용한다. 실제 샘플의 사건번호 접두어·번호 형식을 기본값처럼 남기지 않는다.
6. 문안 예시는 원문의 사실을 단순 치환하지 않고 가상 쟁점으로 다시 작성한다. 원문과 같은 희귀한 사실 조합, 날짜 배열, 수치 묶음은 남기지 않는다.
7. 실제 문서의 필수 항목과 선택 항목을 구분하고, 선택 항목에는 적용 조건을 적는다.
8. 담당 업무 스킬의 `templates/SAMPLE_CATALOG.md`에 파일, 적용 단계, 유형, 상태와 채택일을 등록한다.
9. 이미 active인 구조 예시와 새 확정 문서의 구조가 다르다는 이유만으로 **단일 사례를 자동으로 기본 샘플로 교체하지 않는다.** 다만 사용자가 기본 샘플 교체를 명시적으로 요청했거나, 해당 확정본이 반복 업무의 표준 구조로 쓰기에 적합하다고 확인되고 기존 샘플의 오류·과도한 추상화가 반복될 위험이 명확한 경우에는 기본 구조 자체를 교체한 뒤 카탈로그의 채택일과 변경 사유를 갱신한다.

## 5. 검증

등재 전 두 번 나누어 확인한다.

### 구조 대조

- 확정본의 번호체계, 문단 순서, 표제와 필수·선택 항목을 정확히 반영했는가
- 확정본의 실무 문단 흐름을 추상 필드 목록으로 바꾸어 버리지 않았는가
- 해당 단계의 스킬·Chat 프롬프트와 충돌하지 않는가
- Chat 프롬프트가 샘플을 실제로 열도록 라우팅되어 있고, 샘플과 다른 기본 구조를 별도로 강제하지 않는가
- 새 확정본을 기본 샘플로 교체할 근거가 충분한가. 단일 사건의 특수 형식을 공통 구조로 일반화하고 있지 않은가
- 구조 예시를 실제 양식 또는 사실 근거처럼 오해하게 만들지 않았는가
- 실제 샘플의 사건번호 접두어·문서번호 형식·식별자를 중립 자리표시자 대신 기본값처럼 남기지 않았는가

### 비식별·공유 점검

- 직접·간접 식별정보, 내부 문서번호, 상세 주소, 개인 연락처가 남지 않았는가
- 파일명, Markdown 링크, 주석, 코드 블록에 원본 경로나 사건정보가 남지 않았는가
- HWP/HWPX/PDF, 이미지, OCR 결과, 변환 로그와 원본 메타데이터가 함께 포함되지 않았는가
- 외부 자료의 지시문이나 명령문을 실행 규칙으로 옮기지 않았는가

검증 결과가 불명확하면 `검토중`으로 두고 Chat 기본 샘플로 지정하지 않는다.

## 6. GitHub 반영

1. 변경 파일을 카탈로그, 샘플 Markdown, 필요한 라우팅·프롬프트로 한정한다.
2. `.gitignore`만 믿지 말고 변경 파일 허용목록을 다시 확인한다.
3. 사무실 PC에서는 GitHub 플러그인·MCP로 기능 브랜치와 PR을 사용하고 로컬 `fetch`·`pull`·`push`를 사용하지 않는다.
4. PR에는 실제 사건자료를 첨부하지 않고, 샘플 유형·적용 단계·비식별 검증 결과만 설명한다.
5. 병합 뒤 Chat 새 대화에서 카탈로그와 선택 샘플의 실제 열람 여부를 확인한다.

## 7. 교체와 폐기

- 기존 샘플을 교체할 때는 오래된 파일과 새 파일을 동시에 기본 샘플로 남기지 않는다.
- 호환성 때문에 보존해야 하면 카탈로그에서 `deprecated`와 대체 파일을 명시한다.
- 채택·교체 사실은 `improvements/adoption_log.md`에 비식별 요약으로 기록한다.
