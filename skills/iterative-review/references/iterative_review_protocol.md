# 반복 재검토 프로토콜

## 1. 목적

이미 작성·검토된 산출물을 처음 보는 제3자 관점에서 다시 확인하고, 실질적인 문제를 직접 수정한 뒤 같은 기준으로 재검토를 반복하여 더 이상 의미 있는 수정 필요가 없을 때 종료한다.

이 절차의 목적은 수정 횟수를 늘리는 것이 아니라 **오류·누락·정합성 문제를 줄이고 안정된 최종본에 도달하는 것**이다.

## 2. 적용 대상

다음처럼 **검토 → 직접 수정 → 재검토 반복**의 의도가 명확한 요청에 적용한다.

- 반복 재검토
- 반복검토
- 재검토 반복
- 수정 필요가 없어질 때까지 재검토
- 검토하고 직접 수정한 뒤 다시 재검토를 반복
- 같은 취지의 명시적 반복 검토 요청

`제3자 관점`, `처음 보는 입장`은 검토 방식이며, 그 표현만으로는 반복 루프의 트리거로 사용하지 않는다.

다음은 이 프로토콜의 트리거로 사용하지 않는다.

- `독립검토`
- `독립검토-1`
- `독립검토-2`
- `독립검토-3`
- 기존 블라인드 독립검토·교차검증·레드팀 검토를 의미하는 `독립 재검토`

위 표현은 기존 `prompts/chat_mode/독립검토/` 체계를 우선한다.

## 3. 검토 단위

각 반복은 다음 순서로 수행한다.

### 단계 1 — 제3자 관점 재검토

현재 최종본과 사용자 확정 조건을 기준선으로 고정한다.

다음 항목을 우선 점검한다.

1. 근거 없는 사실 추가 또는 과도한 단정
2. 핵심 쟁점·요구사항·반론 누락
3. 문단·표·결론 사이의 내부 모순
4. 법령·권한·관할·시점·절차 오류
5. 날짜·수치·계산·고유명사·문서번호 오류
6. 담당부서 의견과 최종 판단의 혼동
7. 처리 완료·확인 완료 등 조치상태의 과장
8. 개인정보·민감정보·제3자 정보 노출
9. 사용자가 확정한 조건의 누락 또는 되돌림
10. 산출물의 실제 사용 목적을 방해하는 구조적 문제

### 단계 2 — 직접 수정

실질적 문제가 확인되면 가능한 범위에서 즉시 수정한다.

- 자료로 해결 가능한 문제는 직접 수정한다.
- 추가 사실 확인 없이는 결론을 낼 수 없는 문제는 `확인 필요`로 남긴다.
- 사용자가 확정한 표현은 사실·법령·절차·개인정보·논리 문제가 없는 한 유지한다.
- 문체 취향만을 이유로 전체 문장을 다시 쓰지 않는다.

### 단계 3 — 수정본 재검토

수정된 결과물을 다시 처음 보는 제3자 관점에서 검토한다.

이때 이전 수정의 정당성을 변호하지 말고 다음을 확인한다.

- 새 수정이 다른 문단과 충돌하지 않는가
- 수정으로 새로운 누락이나 모호성이 생기지 않았는가
- 해결한 문제를 다른 표현으로 다시 만들지 않았는가
- 결론·근거·조치방안이 서로 일치하는가

필요하면 다시 수정하고 같은 과정을 반복한다.

## 4. 종료 기준

다음 조건을 모두 만족하면 반복을 종료한다.

1. 새 재검토에서 **정확성·완전성·정합성·안전성·실사용성에 영향을 주는 새로운 수정 필요가 발견되지 않음**
2. 남은 차이가 문체 취향, 동의어 선택, 사소한 압축 여부 수준임
3. 확인 불가능한 사항은 `확인 필요`로 명확히 분리되어 있음
4. 사용자 확정 기준이 최종본에 반영되어 있음
5. 추가 반복이 실질적 품질 향상 없이 표현만 바꾸는 단계에 들어감

첫 재검토에서 실질적 문제가 없으면 즉시 종료한다. 수정이 있었다면 수정본을 최소 한 번 다시 검토하고, 그 재검토에서도 실질적 문제가 발견될 때만 추가 반복한다. 반복 횟수 자체에 목표값이나 최소 횟수를 두지 않는다.

## 5. 금지 사항

- 다른 결론을 일부러 만들어 독립성을 연출하지 않는다.
- 이전 작업자를 비판하기 위한 검토를 하지 않는다.
- 사용자가 요청하지 않은 주변 쟁점을 새 사건처럼 확장하지 않는다.
- 수정할 것이 없는데도 문장을 바꾸지 않는다.
- 같은 쟁점을 표현만 바꾸어 반복 지적하지 않는다.
- 확인할 수 없는 사실을 추정으로 메우지 않는다.
- 반복 횟수를 성과지표처럼 취급하지 않는다.

## 6. 다른 지침과의 결합

- `bold-revision-review`와 함께 요청되면 **반복 재검토로 내용 안정화 → 최종본에 굵은 수정안 형식 적용** 순서로 한다.
- `document-validation-pipeline`이 필요한 결재·대외 문안이면 기존 사건 검토 검증을 재사용하여 반복 재검토 최종본과의 일치만 확인한다. 사건 검토 검증이 없으면 현재 사건 검토를 먼저 한 번 검증하고, 검증 후 근거가 실질적으로 바뀌었으면 영향을 받는 부분만 다시 검증한다. 두 절차가 같은 문제를 중복 생산하지 않도록 한다.
- 기존 `독립검토-1/2/3`이 명시된 경우에는 이 프로토콜 대신 기존 독립검토 체계를 적용한다.
- Codex에서 서브에이전트를 사용할 수 있더라도 반복 재검토 자체가 자동으로 병렬화를 요구하는 것은 아니다. 단일 산출물은 주 에이전트가 직접 처리할 수 있다.

## 7. 최종 보고

사용자가 검토 이력까지 요구하지 않는 한 중간 버전을 모두 제시하지 않는다.

- 현재 작업이 파일·저장소 편집이고 사용자가 수정을 요청한 경우에는 최종 안정본을 해당 파일에 직접 반영하고, 응답에서는 변경 핵심과 최종 검토 상태만 간단히 보고한다.
- 텍스트 작업이면 최종 수정본을 제시한다.
- 최종 패스 결과는 `실질적인 추가 수정 필요 없음` 또는 남은 `확인 필요` 사항으로 정리한다.
