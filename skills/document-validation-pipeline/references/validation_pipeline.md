# 자동 검증 파이프라인 지침

## 1. 목적

최종 회신문, 조사보고서, 검토의견서 등 결재·대외 발송 문안에 대해 근거 누락, 쟁점 누락, 표현 과확장, 날짜·법령 오류, 개인정보 위험을 점검하고 문체 품질을 안정화한다.

자동 검증은 기관의 최종 판단을 대체하지 않으며, 작업을 멈추게 하는 승인 절차도 아니다. 오류 후보, 문체 개선 지점, 확인 필요 사항을 도출하는 보조 절차이다.

## 2. 입력 파일

기본 입력 파일은 다음과 같다.

- `BASE_INSTRUCTIONS.md`
- `public_interest_report_checklist.md` (공익신고 사건으로 판단된 경우 초반에 숙지하고 필요 시 참조)
- `claim_classification_matrix.md`
- `department_review_matrix.md`
- `working_checkpoint.md`
- `final_reply_draft.md`

사건별로 파일명이 다르면 같은 역할의 파일을 찾아 대체한다.

| `hwpx_quality_check.md` | 최종 HWPX 작성·편집 품질 검증 결과. HWPX 제출본을 만든 경우에만 작성 |

## 4. 검증 항목

### 4.1 주장 분류 반영 여부

- A. 공익신고 검토 대상이 회신문에 반영되었는지 확인한다.
- B. 감사·민원 참고사항이 실체 판단처럼 표현되지 않았는지 확인한다.
- C. 실체 판단 제외사항이 타 기관 소관 또는 별도 절차로 안내되었는지 확인한다.
- D. 공익신고 사건인 경우 `public_interest_report_checklist.md`의 검토 대상성 분류와 충돌하지 않는지 확인한다.

### 4.2 부서별 조사결과 반영 여부

- 조사요청 공문상 쟁점이 누락되지 않았는지 확인한다.
- 부서별 조사결과와 최종 문안의 결론이 충돌하지 않는지 확인한다.
- 담당부서 회신 또는 제출자료를 감사부서의 최종 판단처럼 단순 전재하지 않았는지 확인한다.
- 대외 문안이 `담당부서 확인 결과`, `소관부서 확인 결과`처럼 책임을 넘기는 구조로 읽히지 않는지 확인한다.
- 감사부서 또는 회신부서가 제출자료와 관계자료를 재확인한 뒤 회신한다는 처리 구조가 드러나는지 확인한다.
- 소관 법령이 다른 조사결과를 모순으로 오인하지 않는다.
- 사건 발생지와 관할 구청·읍면동·본청·사업소·외부기관 여부를 고려한 소관부서 확인이 필요한지 점검한다.

### 4.3 확인 필요 항목 처리

- `working_checkpoint.md`의 확인 필요 항목이 최종 문안에서 확정 표현으로 바뀌지 않았는지 확인한다.
- 확인이 끝나지 않은 사항은 `[확인 필요]`, `제출자료만으로 단정하기 어려움`, `소관부서 확인 필요` 등으로 처리한다.
- 담당부서 자료를 재확인하지 않은 상태에서 확정 회신문으로 작성된 문장이 있는지 확인한다.
- 재확인이 부족한 사항은 결론 문안으로 쓰기 전에 원자료 확인, 소관부서 추가 확인, 법령·규정 확인, 개인정보 공개범위 확인 중 필요한 항목으로 분리한다.
- 잠정 판단이 최종 문안에서 확정 판단처럼 표현되지 않았는지 확인한다.
- `[법령 확인 필요]`, `[당시 법령 확인 필요]`, `[별표·시행령 확인 필요]`, `[소관 권한 확인 필요]`로 표시된 사항이 최종 문안에서 단정 표현으로 바뀌지 않았는지 확인한다.

### 4.4 표현 수위 점검

다음 표현은 근거 수준과 맞는지 확인한다.

- 명백한
- 위법
- 특혜
- 비리
- 포탈
- 고의
- 허위
- 유착
- 방치
- 확인됨
- 완료

필요한 경우 다음처럼 완화한다.

| 위험 표현 | 권장 표현 |
|---|---|
| 위법 확인 | 위반사항이 확인된 것으로 회신됨 |
| 특혜 | 형평성 문제 제기 |
| 포탈 | 부과·징수 적정성 의혹 |
| 완료 | 완료된 것으로 회신됨 |
| 문제 없음 | 조사결과 위반사항은 확인되지 않음 |

### 4.5 법령 확인

법령을 인용한 경우 다음을 확인한다.

- 법령명
- 조문번호
- 시행일
- 당시 시행 법령과 현재 시행 법령 구분 필요 여부
- 시행령·시행규칙·별표 확인 필요 여부
- 법령 효과와 소관 권한 구분 여부
- 법령 확인 상태와 회신문 표현 수위의 일치 여부
- 확인한 공식 출처와 확인일
- 원문 미확인, 접속 실패, 권한 제한 자료가 결론에 미치는 영향

### 4.6 개인정보·비공개 정보

대외 문안에 다음 정보가 불필요하게 포함되었는지 확인한다.

- 개인 성명
- 연락처
- 주소 세부정보
- 내부 담당자명
- 신고자 식별 가능 정보
- 제3자 재산·금융 관련 세부정보
- 공유 또는 인수인계 대상 폴더의 `.env`, API 키, 변환 로그, OCR 결과, `output/`, `_validation/`, HWPX 내부 미리보기 텍스트와 이미지

### 4.7 최종 기준 파일과 마무리 단계 지시사항 반영 여부

- 검증 대상 문서가 사용자가 지정한 `최종 기준 파일`과 일치하는지 확인한다.
- 이전 초안, 폐기된 문안, 참고용 검토파일을 최종본으로 오인하지 않았는지 확인한다.
- 최근 대화에서 새로 합의한 문체, 번호체계, 공개 범위, 담당부서 표기, 굵게 표시, 연락처 정리 등 지시사항은 매번 점검하지 않는다.
- 사용자가 작업 마무리, 인수인계, 최종 검증, 지침 업그레이드를 요청하거나 최종 산출물을 확정하는 단계에서만 최근 지시사항을 목록화한다.
- 마무리 단계에서는 각 지시사항의 최종본 반영 상태를 `반영`, `미반영`, `확인 필요`, `의도적으로 제외`로 표시한다.
- `의도적으로 제외`한 경우에는 제외 사유를 짧게 남긴다.
- 사용자가 결재 문체, 발송 화면 가독성, 책임 범위 등을 이유로 검토자 권장 문안을 채택하지 않았다고 명시한 경우, 이를 `사용자 확정 기준`으로 기록하고 같은 사항을 미반영 오류처럼 반복 지적하지 않는다.
- `현재까지 확인된 자료상`, `현재 확인된 자료만으로는` 등 한정 표현이 반복되어 자료 확인 책임을 미루는 인상으로 읽히지 않는지 점검한다. 단, 판단 범위를 제한해야 하는 핵심 문장에는 필요한 만큼 사용한다.

### 4.8 HWPX 작성·편집 품질

최종 제출용 HWPX를 생성하거나 기존 양식에 문안을 반영한 경우 다음을 확인한다.

검토 완료된 최종 기준 문안을 내용 변경 없이 HWPX로 옮기는 `빠른 HWPX` 작업은 기존 사실·법령·문체 검증을 재사용한다. 이 경우 아래 항목 중 본문 일치, 패키지 구조, 샘플 잔여 문구, 스타일 참조, 마크다운 잔여 표시와 시각 확인 상태만 점검한다. 결재·발송 최종본이거나 문안이 바뀐 경우에는 전체 항목을 적용한다.

`샘플을 참조해서 HWPX 초안을 만들어줘`, `검토한 내용대로 HWPX로 제공해줘`처럼 동일 취지의 요청도 빠른 HWPX 조건을 충족하면 같은 범위로 처리한다. 경고가 없는 초안은 별도 검증보고서를 만들지 않고 짧은 통과 요약만 남기며, 인수인계·샘플 색인·자료목록은 별도 요청 또는 최종화·마무리 단계가 아니면 갱신하지 않는다.

- 기준 HWPX 양식 또는 변환본과 최종 MD 기준본이 일치하는가
- 기존 문단·표·셀·글상자·스타일 참조를 보존하는 방식으로 반영했는가
- `Contents/header.xml`의 스타일 ID와 `Contents/section*.xml`의 `charPrIDRef`, `paraPrIDRef` 참조가 일치하는가
- 자간, 장평, 줄간격, 글꼴 크기가 기존 본문 스타일과 다르게 튀지 않는가
- 문자 속성의 `height`, `ratio`, `spacing`, `useKerning`, `useFontSpace`, 글꼴 참조가 의도치 않게 바뀌지 않았는가
- 표 폭, 셀 병합, 셀 안쪽 여백, 글머리, 작성정보 위치가 유지되었는가
- `content.hpf`, `META-INF/manifest.xml`, section XML, `BinData/` 참조가 유효한가
- `Preview/PrvText.txt`가 오래된 본문을 보여주지 않는가
- 마크다운 표시(`**`, `#`, 표 구분자 등)나 깨진 한글이 남지 않았는가
- 실제 한글 프로그램 또는 HWPX 뷰어에서 열어 확인했는가. 확인하지 못했으면 `시각적 서식 확인 필요`로 남긴다.
- XML·텍스트 추출 결과에서 보이는 들여쓰기, 번호 뒤 띄어쓰기, 문단 간격 문제가 실제 한글 프로그램 또는 발송 시스템 화면에서도 문제인지 구분했는가
- 사용자가 실제 발송 화면 기준으로 확정한 표기 방식을 XML 추출 결과만 보고 되돌리지 않았는가

## 5. 검증 결과 표기 방식

검증 결과는 다음 형식으로 작성한다.

| 구분 | 의미 |
|---|---|
| `[확인 완료]` | 근거자료와 최종 문안이 일치 |
| `[확인 필요]` | 원문 또는 소관부서 확인 필요 |
| `[문안 수정 권고]` | 표현 수위 또는 문장 구조 수정 필요 |
| `[누락 가능]` | 조사요청 또는 주장 분류 대비 회신문 반영 부족 |
| `[위험]` | 개인정보, 관할, 법령, 단정 표현 등 결재 전 수정 필요 |

## 6. 최종 보고 방식

최종 답변에는 다음 순서로 보고한다.

1. 검증 수행 여부
2. 주요 오류 후보
3. 수정 권고 문안
4. 확인 필요 항목
5. 남은 위험
6. 최종 반영 전 확인 필요 요약

`최종 반영 전 확인 필요 요약`은 형식적 체크리스트 반복이 아니라 검증 결과에 따른 실제 확인 필요 항목만 요약한다.

- 추가 확인이 필요한 사항이 있으면 어느 부분을 확인해야 하는지 구체적으로 적는다.
- 확인 필요 항목은 필요에 따라 담당부서 제출자료와 원자료의 일치 여부, 감사부서 또는 회신부서의 재확인 범위, 확인 필요 사항의 확정 표현화 여부, 법령·규정 확인 필요 여부, 제3자 개인정보 공개범위 등으로 나누어 쓴다.
- 추가 확인이 필요한 사항이 발견되지 않았으면, `추가 확인 필요 항목은 발견되지 않았으며, 최종 반영 시 문단 번호·굵게 표시 범위 등 형식만 확인하면 됩니다.`처럼 남은 위험을 한정해 보고한다.

## 7. 마무리 단계 지시사항 반영표 형식

작업 마무리, 인수인계, 최종 검증, 지침 업그레이드 단계에서 필요한 경우 다음 표를 검증 산출물에 포함한다.

| 최근 지시사항 | 최종본 반영 상태 | 근거 위치 | 비고 |
|---|---|---|---|
| 예: 소제목에 담당부서 표시 | 반영 | 본문 가.~사. 소제목 |  |
| 예: `○` 대신 `1) 2) 3)` 사용 | 반영 | 본문 세부 항목 |  |
| 예: 특정 표현 제외 | 확인 필요 | 해당 문단 | 결재 전 재확인 |
