# OpenCodex xAI/Grok 런타임 어댑터

> 적용 범위: 사용자가 `lidge-jun/opencodex`에서 xAI/Grok 구독 모델로 **수동 전환한 뒤**, Codex·Grok Build 등 지원 클라이언트에서 `m1` 지침을 계속 사용하는 경우
>
> 확인 기준: 2026-08-31, `lidge-jun/opencodex` main `c7d8407d29bdd98b7ba743c85e654a41b3e4fca8`

## 1. 지위

이 문서는 OpenCodex를 통해 xAI/Grok 모델을 사용하는 세션에서 기존 `m1`을 그대로 적용하기 위한 **런타임 어댑터**다.

- 모델·공급자 전환은 사용자가 OpenCodex에서 직접 선택한다. 이 지침이나 에이전트가 Codex 한도·품질 등을 이유로 자동 전환하지 않는다.
- Codex 클라이언트 안에서 OpenCodex로 `xai/grok-*`를 쓰는 경우에도 기본 실행 라우터는 `AGENTS.md`다.
- `GROK_ENTRYPOINT.md`는 Grok 일반 Chat 전용이며 이 경로에 적용하지 않는다.
- 업무별 정본·스킬·하네스는 기존 `m1`을 그대로 쓰고, 이 문서는 공급자·모델·클라이언트가 바뀔 때 생기는 실행환경 차이만 보정한다.
- 과거 Gemini용 OpenCodex 경로를 되살리는 것이 아니다. 사용자가 선택한 xAI/Grok 구독 경로만 현재 운용 대상으로 둔다.

## 2. 적용 게이트와 전환 책임

다음 중 하나일 때 적용한다.

1. 현재 Codex 계열 세션이 OpenCodex를 통해 `xai/grok-*`로 라우팅되고 있음이 실제로 확인된다.
2. 사용자가 현재 세션을 OpenCodex의 xAI/Grok 모델로 **이미 수동 전환했다고** 밝힌다.

`Grok으로 바꾸`, `OpenCodex로 전환해`처럼 아직 실행되지 않은 전환 요청 자체를 이 문서의 적용 완료 상태로 해석하지 않는다. 실제 모델 선택·전환은 사용자가 직접 수행한다.

다음은 이 지침이 하지 않는다.

- Codex 사용량을 감시해 Grok으로 자동 전환
- 모델 picker·기본모델·combo를 임의 변경
- 다른 OpenCodex 지원 클라이언트로 자동 전환
- 품질 비교만으로 공급자를 자동 교체
- 사용자가 요청하지 않은 설치·로그인·서비스 시작

Codex 한도 부족은 사용자가 Grok으로 바꾸는 **이유**일 수 있지만, 지침의 자동 전환 트리거가 아니다. 현재 어떤 모델·클라이언트를 쓸지는 사용자가 결정한다.

## 3. xAI 인증과 비용 경계

OpenCodex의 현재 xAI OAuth 경로는 `ocx login xai`이며, 별도 Grok CLI 구독 게이트웨이를 사용한다. xAI API 키 경로와는 별개다.

- 사용자가 Grok 구독 경로를 설정한 경우 그 인증 방식을 유지한다.
- `SuperGrok`, X 유료 플랜 등 구독명만 보고 OpenCodex용 xAI OAuth 코딩 권한이나 특정 모델 사용권을 단정하지 않는다. 현재 로그인한 xAI 계정에서 실제 노출되는 모델·권한을 확인한다.
- 별도 xAI API 종량제 키를 사용자가 명시하지 않았다면 API 키 경로로 임의 전환하지 않는다.
- 모델 목록은 live discovery가 우선이므로 `grok-4.5`, `grok-4.6` 같은 현재 예시를 영구 고정하지 않는다.
- 실제 모델 id·reasoning 단계·가용성은 현재 OpenCodex와 xAI 계정에서 확인된 값만 사용한다.

설치·로그인·업데이트를 실제 수행할 때는 OpenCodex의 현재 `AGENTS_INSTALL.md`와 공식 문서를 먼저 확인한다. 패키지 설치, 서비스 등록, 계정 로그인은 사용자가 요청한 범위에서만 수행한다.

## 4. Codex quota gate·Desktop picker 주의

OpenCodex 문서상 Codex 앱이 네이티브 5시간 한도를 소진하면 reserve fallback 상태에서 routed OpenCodex 모델까지 picker에서 숨기거나 비활성화할 수 있다. 이 제한은 요청이 프록시에 도달하기 전에 Codex 클라이언트가 적용할 수 있다.

Codex Desktop은 이와 별개로 원격 allowlist 때문에 routed 모델이 picker에서 빠질 수 있다. picker에 없다는 사정만으로 OpenCodex/xAI 인증 실패로 단정하지 않는다.

따라서:

- routed 모델이 picker에서 사라졌다고 OpenCodex/xAI 인증 실패로 단정하지 않는다.
- 현재 live model id의 직접 라우팅 가능 여부를 확인할 수는 있으나, Codex 클라이언트가 요청 자체를 막으면 프록시 설정을 반복 변경하지 않는다.
- 다른 OpenCodex 지원 클라이언트가 대안일 수 있음을 보고할 수는 있지만, **사용자 지시 없이 모델·클라이언트를 바꾸거나 새 클라이언트를 설치하지 않는다.**
- 한도 소진 전에 Grok으로 바꿀지, 소진 뒤 다른 클라이언트를 쓸지는 사용자 운영 선택으로 둔다.

## 5. 작업 연속성과 인수인계

모델 전환 자체는 새로운 자동 인수인계 트리거가 아니다.

- 인수인계 작성·갱신 조건과 내용은 기존 정본인 `prompts/create_handoff.md`를 따른다. 이 문서에서 별도 형식이나 필수 항목을 다시 정의하지 않는다.
- 사용자가 모델 전환을 위해 `인수인계`, `이어 작업할 자료`, `다음 모델에 넘길 정리` 등을 요청하면 `prompts/create_handoff.md`를 적용한다.
- 기존 `m1`의 다른 마무리·인수인계 트리거는 그대로 유지한다. 이 문서는 그 범위를 넓히거나 좁히지 않는다.
- 새 Grok 세션에서는 제공된 `HANDOFF_SUMMARY.md`를 시작점으로 읽되, 인수인계서는 스냅샷이므로 실제 브랜치·파일·diff·PR 상태를 다시 확인한다.
- 인수인계서가 없으면 이전 모델의 대화 기억이나 미기록 결정을 추정하지 않는다. 현재 저장소에서 확인 가능한 상태만 기준으로 작업한다.
- 같은 작업트리를 쓰더라도 사용자가 인수인계서를 요청했다면 생략하지 않는다. 반대로 모델 전환만으로 별도 인수인계를 자동 생성하지 않는다.

즉 **모델 전환은 인수인계 규칙을 새로 만들지 않으며**, 실제 작성 여부와 내용은 기존 `m1` 인수인계 정본이 결정한다. Git 작업트리와 저장소 상태는 인수인계 내용을 검증하는 기준선으로 사용한다.

## 6. 하네스와 서브에이전트

OpenCodex xAI/Grok 경로에서는 `guides/harness_structure_guide_v1_3.md`의 **분해·소유권·검증·완전성 원칙**은 유지하되, Luna·Terra·Sol이라는 모델명과 비용비율을 Grok에 기계적으로 대입하지 않는다.

**Grok의 모델·reasoning·프로필 배정은 이 절을 정본으로 한다.** 별도의 Grok 하네스를 통째로 복제하지 않으며, 기존 하네스의 Sol·Terra·Luna 모델 배정·크레딧 비율·GPT 전용 승격 규칙은 Grok 경로에 적용하지 않는다. Grok 경로에서는 공통 역할 원칙만 재사용하고, 모델별 실행값은 이 런타임 어댑터로 치환한다.

- 현재 주 모델이 Grok이면 그 모델이 오케스트레이터 역할을 맡을 수 있다.
- 서브에이전트는 현재 클라이언트와 OpenCodex가 실제 제공하는 경우에만 사용한다.
- OpenCodex가 routed `provider/model`을 서브에이전트 후보로 노출할 수 있어도 실제 가용 모델과 모델 수는 현재 런타임을 확인한다.
- 모델별 reasoning 단계는 해당 xAI 모델이 현재 노출하는 단계만 사용하고 GPT용 `ultra`, `max` 등의 규칙을 그대로 가정하지 않는다.
- 분해 위험 업무, 최종 통합 책임, 같은 파일 동시 수정 금지 등은 기존 하네스 규칙을 유지한다.

2026-09-01 확인한 Grok 전용 배정은 다음과 같다. 구독 경로이므로 Codex 크레딧의 Sol·Terra·Luna 단가 비율을 기대하지 않는다.

- 주 담당: `xai/grok-4.6`. 최종 판단·통합. 하위 작업 기본값으로 복제하지 않는다.
- 관계·예외 검토: `xai/grok-4.3` medium 또는 프로필 `grok_reviewer`. 실제 호출에서 `grok-4.3` 응답을 확인했다.
- 반복 추출·대조: `xai/grok-4.3` low 또는 프로필 `grok_worker`. 실제 호출에서 `grok-4.3` 응답을 확인했다.
- `xai/grok-4.20-0309-non-reasoning`과 `xai/grok-4.20-0309-reasoning`은 picker에 보일 수 있어도, 현재 `spawn_agent`가 `reasoningEffort`를 붙여 400으로 거부한다. 기본 하위 작업 모델로 쓰지 않는다.
- `grok-4.5`, `grok-4.20-multi-agent-0309`, `grok-build-0.1`, `grok-composer-2.5-fast`는 이 목적의 하위 작업에 넣지 않는다.
- 하위 작업 목록이 바뀐 뒤에는 현재 열린 작업이 아니라 새 작업에서 실제 선택 목록과 호출 성공 여부를 다시 확인한다.

서브에이전트 지원이 없거나 불안정하면 단일 Grok 세션으로 처리하며, 없는 기능을 흉내 내기 위해 별도 자동화나 외부 호출을 만들지 않는다.

## 7. 개인정보·비공개 자료 경계

xAI/Grok은 기존 `m1` 하네스에서 말하는 GPT 공급자와 다른 외부 공급자다. 따라서 공급자 경계를 완화하지 않는다.

- `coding`, `m1` 등 개인정보·비공개 사건 원문이 없는 코드·지침 작업은 저장소의 기존 공유 범위 안에서 사용할 수 있다.
- 민원·감사·공익신고 등 개인정보·민감정보·비공개 사건 원문은 Grok으로 자동 전달하지 않는다.
- Grok 사용이 꼭 필요하면 최소 범위로 마스킹·검증하고, 대상 서비스와 목적을 사용자에게 알린 뒤 외부 전송 승인을 받은 범위만 사용한다.
- 기존 GitHub·외부 서비스 전송 금지 자료는 OpenCodex를 쓴다는 이유로 허용되는 것이 아니다.

## 8. 도구와 파일 작업 경계

OpenCodex는 모델 공급자를 바꾸는 프록시다. 실제 파일·셸·Git·GitHub·서브에이전트 기능은 **현재 클라이언트가 제공하는 도구**를 기준으로 판단한다.

- Codex에서 Grok을 쓰더라도 현재 세션에 로컬 파일·셸 도구가 제공되면 그 범위에서 사용할 수 있다.
- Grok 일반 Chat의 GitHub 커넥터 제한을 OpenCodex-routed Codex에 그대로 적용하지 않는다.
- 반대로 모델이 Grok이라는 이유만으로 Codex의 모든 도구가 반드시 작동한다고 가정하지 않는다. 실제 호출 성공 여부를 확인한다.
- 수행하지 않은 빌드·테스트·원본 판독·Git 작업을 수행했다고 표현하지 않는다.

## 9. 수동 전환 뒤의 기본 동작

사용자가 OpenCodex에서 Grok 모델로 바꾼 뒤 새 작업을 시작하면, 현재 런타임이 xAI/Grok임을 확인한 후 이 문서를 적용한다.

이때 모델을 다시 고르거나 전환을 제안하는 것이 아니라 다음만 수행한다.

1. `AGENTS.md`와 현재 업무에 필요한 지침을 적용한다.
2. 사용자가 제공한 인수인계서가 있으면 읽고 실제 저장소 상태와 대조한다.
3. 인수인계서가 없으면 현재 저장소에서 확인되는 상태부터 파악한다.
4. Grok 런타임에서 실제 제공되는 도구·모델·reasoning 경계만 보정해 기존 작업 절차를 수행한다.

Grok 일반 Chat에서 독립검토를 하려는 경우에는 이 문서가 아니라 `GROK_ENTRYPOINT.md`를 사용한다.

## 10. 상류 변경 확인

OpenCodex는 빠르게 변경되는 외부 프로젝트이므로 설치·인증·모델 라우팅·Codex quota 제한을 장기 고정 사실로 취급하지 않는다. 실제 설정 또는 장애 대응 전에 아래 상류 자료를 최신 main 기준으로 다시 확인한다.

- `docs-site/src/content/docs/guides/codex-app-models.md`
