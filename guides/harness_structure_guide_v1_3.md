# 서브에이전트 병렬 작업 구조 운용 지침

> **문서 버전**: v2.23\
> **개정일**: 2026-10-20\
> **파일명 안내**: `harness_structure_guide_v1_3.md`는 기존 프롬프트와 사건 폴더의 참조 호환을 위해 유지한다. 현재 적용 버전은 이 문서의 `문서 버전`을 기준으로 판단한다.
> **적용 범위**: Codex·Work·Hermes 등 현재 세션에서 실제 도구로 작업을 수행하고, 허용된 서브에이전트 위임 기능이 제공되는 환경에서 복합 태스크를 분석·분해·위임·검증할 때. 일반 Chat의 설명·질문에는 병렬 위임 하네스를 적용하지 않는다. 단, 5.2절의 모델·reasoning 선택 기준은 서브에이전트 사용 여부와 무관하게 해당 모델의 reasoning effort를 선택하는 경우 공통 참조한다.
> **핵심 원칙**: 하네스는 항상 적용하는 절차가 아니다. 서브에이전트 사용은 현재 세션 정책과 도구 가용성을 우선하며, 독립적이고 범위가 명확한 작업에서 실질적인 속도 또는 검증 이점이 있을 때 적용한다.

---

## 1. 개념 정의

**하네스 적용 판단** = 요청을 바로 실행하기 전에 작업 단위, 산출물, 로그, 검증 흐름을 별도로 설계할 필요가 있는지 판단하는 단계.

**병렬 작업 구조** = 본 에이전트 1개가 오케스트레이터 역할을 맡고, 필요 시 독립적인 서브에이전트가 제한된 하위 작업을 병렬로 수행하는 구조.

오케스트레이터는 다음을 책임진다.

- 요청 목적과 제약 파악
- 태스크 분해
- 직접 처리할 핵심 경로와 위임 가능한 보조 경로 구분
- 서브에이전트 지시문 작성
- 결과 검토·통합
- 최종 산출물 품질 확인

서브에이전트는 본 에이전트를 대체하지 않는다. 최종 판단, 파일 반영, 사용자 보고 책임은 오케스트레이터에게 있다.

---

### 1.1 실행 모드 구분

- 일반 Chat의 설명·질문·문안 검토에는 병렬 위임 절차를 적용하지 않는다. 모델·reasoning 선택이 필요한 경우의 5.2절 참조는 별개다.
- 채팅 화면에서도 Hermes 등이 실제 도구로 작업을 실행하면 작업 실행 환경으로 판단한다. AGENTS를 읽거나 모델 이름을 언급했다는 사실만으로 위임 기능이 있다고 간주하지 않는다.
- Codex·OpenCodex, Work, Hermes의 도구·호출 인수·모델 지정 방식은 서로 대입하지 않는다. 실행환경별 경로는 3.3.2절을 따른다.

---

## 2. 하네스 적용 판단

하네스 지침은 다음 경우에 먼저 확인한다.

- 사용자가 `하네스`, `팀 작업`, `병렬`, `나눠서`, `여러 에이전트`, `대량`, `반복`, `여러 산출물`, `다음 대화방에서 이어서`를 언급한 경우
- 산출물이 2개 이상이고 서로 다른 검토 흐름이 필요한 경우
- 대량 파일, 대량 행, 여러 부서 자료처럼 누락 위험이 큰 경우
- 다른 대화방이나 다른 컴퓨터에서 이어갈 가능성이 있어 로그 또는 인수인계가 필요한 경우

다음 경우에는 하네스 없이 진행할 수 있다.

- 단일 문안 수정
- 짧은 검토 의견 작성
- 파일 1~2개 확인 후 답할 수 있는 작업
- 단순 오탈자 또는 표현 정리
- 사용자가 이미 작업 순서를 명확히 준 경우

하네스를 적용하더라도 항상 서브에이전트를 쓰는 것은 아니다. 서브에이전트 없이도 작업 단위, 로그, 산출물, 검증 흐름만 간단히 설계할 수 있다.

---

## 3. 병렬 구조 사용 조건

서브에이전트 위임을 지원하는 환경에서는 병렬 에이전트를 기계적으로 사용하지 않는다. 아래 조건을 모두 만족할 때 사용한다.

1. 현재 세션의 상위 실행정책과 사용 가능한 도구가 서브에이전트 사용을 허용한다.
2. 하위 작업이 구체적이고 범위가 명확하며 서로 독립적이다.
3. 병렬화가 실제 처리시간을 줄이거나 교차검증 품질을 높인다.
4. 같은 파일이나 같은 판단 지점을 동시에 수정하지 않으며, 본 에이전트가 결과를 검토·통합할 수 있다.

사용자가 "서브에이전트", "위임", "병렬 에이전트", "여러 에이전트로 나눠서"라고 요청한 경우는 적극적인 적용 신호이지만 필수 조건은 아니다. 서브에이전트 사용은 사용자가 허용한 범위나 외부 변경 권한을 확대하지 않는다.

### 3.1 주 오케스트레이터의 분해 위험 게이트

업무 분해 여부와 분해 단위는 현재 주 오케스트레이터가 직접 결정하며 하위 모델에 위임하지 않는다. 기본 GPT 경로에서는 Sol이 이 역할을 맡는다. 위임 전에는 다음을 먼저 확인한다.

- 결론이 여러 문서의 관계, 예외·경과규정, 시점, 권한 또는 반대자료에 따라 달라지는가
- 각 하위 과제를 다른 결과 없이 독립적으로 검증할 수 있고, 누락도 발견할 수 있는가
- 근거 위치와 미확인·충돌 자료를 인계할 수 있는가
- 위임·인계·재검증 비용이 주 오케스트레이터의 직접 처리보다 실질적으로 작은가

첫 항목에 해당하거나 나머지를 충족하지 못하면 `분해 위험 업무`로 본다. 이때는 문서별로 결론을 나누지 않고 주 오케스트레이터가 최초 쟁점과 핵심 맥락을 유지하며, 서브에이전트에는 추출·탐색·모순 점검 같은 역할만 맡긴다. 최종 판단 전에는 주 오케스트레이터가 결정적 원문을 직접 대조한다. 비용 절감은 주 오케스트레이터의 판단을 대체하는 것이 아니라 반복 탐색·형식 작업을 줄이는 방식으로 달성한다.

적합한 예시는 다음과 같다.

| 유형 | 예시 |
|---|---|
| 독립 코드 영역 분석 | 프론트엔드 상태 관리와 백엔드 API 라우팅을 별도로 조사 |
| 독립 파일군 수정 | 충돌 없는 모듈 A/B를 각각 수정 |
| 교차 검토 | 구현 중 본 에이전트가 진행하고, 서브에이전트가 테스트 실패 원인만 조사 |
| 대량 자료 분류 | 서로 의존하지 않는 문서 묶음을 기준별로 나누어 정리 |

직접 처리해야 하는 경우는 다음과 같다.

- 하위 과제의 범위와 기대 산출물을 명확히 나누기 어려운 경우
- 다음 단계가 바로 특정 조사 결과에 막혀 있는 경우
- 하위 작업이 같은 파일을 동시에 수정해야 하는 경우
- 예상 서브에이전트 수가 1개뿐이고 병렬 이점이 작은 경우
- 사용자가 빠른 단일 답변을 요구한 경우

### 3.2 자료 처리·승인·컨텍스트 경계

- PDF·HWPX 원본과 로컬 추출본을 읽는 기본 경로에서는 개인정보 마스킹을 자동 실행하지 않는다. 마스킹은 사용자 또는 적용 작업 프로필이 명시한 경우에만 수행한다.
- 마스킹이 필요한 경우에는 실행 전에 대상, 적용 범위, 원본·추출본·산출물 중 적용 위치를 확인한다. 담당 직원 성명·업무 연락처 등 업무 수행·검증에 필요한 정보는 사용자가 허용하거나 작업 프로필이 정한 범위에서 보존할 수 있다. 원본에 이미 존재하는 마스킹·가림 정보는 추정·복원·전사하지 않는다.
- AI 자동 실행은 GUI·BAT보다 설치 스킬의 안정된 PowerShell 래퍼를 우선한다. 텍스트 PDF의 AI 검토용 마스킹은 `run_repo_pdf_to_md.ps1 -MaskPii`, 스캔 PDF·이미지는 `run_repo_pdf_utility.ps1 -Tool oneocr-mask`의 `masked-text` 또는 `visual-mask`, HWPX 추출은 `read_hwpx_text.ps1 -MaskPii`를 사용한다. 각 스위치가 없으면 비마스킹 기본 경로를 유지한다.
- 개인정보·민감정보·비공개 자료 원문은 모델 위임이 허용된 경우에도 `AGENTS.md`의 공급자 경계를 따른다. 다른 공급자 모델이 꼭 필요하면 최소 범위로 마스킹·검증한 뒤 대상·서비스·목적을 알리고 명시 승인을 받는다.
- 외부 OCR·변환과 병렬 위임은 승인 범위를 확대하지 않으며, 마스킹은 외부 전송 승인을 대신하지 않는다.
- 위임 전에는 작업별 `최소 충분 컨텍스트`를 정한다. 관련 최신 대화, 직접 필요한 파일·쪽·절, 확인된 사실과 미확인 쟁점만 전달하되, 결론을 바꿀 반대자료·예외·시점 정보까지 줄여서는 안 된다. 전체 대화·전체 저장소·불필요한 원문은 관성적으로 fork하거나 다시 읽지 않는다.
- 다문서·고위험 작업은 자료 식별자별로 `읽음 / 사용 / 제외(사유) / 미확인 / 판독 불가`를 기록해 누락을 확인한다. 소규모·저위험 작업에는 이 대장을 기계적으로 만들지 않는다.
- 오케스트레이터는 조사 항목, 담당 에이전트, 확인 근거, 완료 상태를 짧게 기록한다. 서브에이전트 결과는 확인 사실, 근거 위치, 충돌 자료, 미확인 범위와 확신도 중심으로 받아 통합하며, 요약만으로 고위험 결론을 승인하지 않는다.

### 3.3 내장 서브에이전트 컨텍스트·동시성 게이트

- 서브에이전트 위임은 현재 도구가 지원하는 최소 컨텍스트 전달을 기본으로 한다. `spawn_agent` 등 도구별 인수는 해당 실행환경에서만 적용한다. `fork_context`를 제공하면 `false`와 독립된 작업 패킷을 사용하고, `fork_turns`를 제공하는 환경에서만 `"none"` 또는 필요한 최근 턴을 지정한다. 지원되지 않는 필드를 보내지 않는다. 전체 대화 상속은 검토자·주 오케스트레이터가 장기 맥락을 직접 유지해야 하고 중복 비용보다 검증 이점이 큰 예외에만 사용하며, 이유를 남긴다.
- GPT-6 Luna는 범위·제약·검증 기준이 명확한 보조 작업의 우선 후보다. 추출·분류·대조뿐 아니라 소유 범위가 정해진 수정·구현, 허용 도구를 사용하는 조사, 제한된 다문서 대조에도 배정할 수 있다. 파일 수정·복합 도구 사용 자체를 이유로 Sol에 넘기지 않으며, 실제 읽기/쓰기 권한과 소유권을 확인한다. 쟁점 설정·결정적 원문 대조·최종 통합은 주 오케스트레이터가 맡는다.
- Luna의 effort는 지원 기본값과 기존 대표 과제 결과에서 출발한다. 누락 민감형은 `high`, 명확한 제약 안에서 관계·모순을 풀어야 하는 보조 검토는 `xhigh`를 평가 후보로 두고, 남은 구체적 추론 문제가 있을 때 `max`를 검토한다. 기존에 효과가 확인된 `max`는 유지할 수 있으나 Terra 대체라는 이유만으로 모든 작업에 고정하지 않는다. 높은 effort는 누락·판독 실패·출력 잘림의 대사를 대신하지 않는다.
- Luna의 예상 입력 20,000토큰은 기존 운영의 작은 패킷 목표이며 모델의 공식 한도나 일률적 승격 기준이 아니다. 입력이 커지면 출력 잘림·완전성 대사·공통 문맥 중복과 실제 처리 결과를 확인해 패킷 축소, 검토자 위임 또는 주 오케스트레이터 직접 처리 중 하나를 선택한다.
- 같은 대화의 Luna 실행은 필요한 최소 수부터 사용한다. 패킷이 작고 경계가 분명하며 대형 공통 문맥을 중복하지 않는 독립 작업은, 병렬화가 시간 단축 또는 교차검증 품질 향상에 실질적으로 기여하고 그 이점이 위임·인계·통합·재검증 비용을 상회할 때에만 현재 실행환경이 허용하는 범위에서 병렬화한다. 저장소 자체에서는 모델별 또는 고정된 동시 실행 상한을 두지 않으며, 상위 실행정책과 실제 세션·도구 제한, 런타임이 허용·배정한 가용 동시성, 단일 쓰기 소유권을 우선한다. 추가 병렬 웨이브의 한계효용이 작아지면 더 생성하지 않는다.
- 프로필은 이름보다 실제 `model`·effort·읽기/쓰기 권한으로 선택한다. `luna_worker`·`terra_reviewer` 같은 구형 이름이 GPT-5.6에 고정되어 있으면 현재 Luna 6·Sol 6.1 배정을 구현한 것으로 보지 않고 기본 후보로 자동 호출하지 않는다. 모델 미지정 기본 보조 모델도 별도로 확인하고, GPT 제한 자료에 다른 공급자의 기본값이 적용되지 않도록 한다. 현재 도구가 지원하면 `model`·`reasoning_effort`를 직접 지정하며, 적합한 프로필도 직접 지정도 지원하지 않으면 본 에이전트가 처리한다. 위임 대신 새 사용자 채팅을 만들지 않는다.
- 주 에이전트의 모델 선택이 서브에이전트 모델을 자동으로 보장한다고 간주하지 않는다. 위임 전에 현재 도구가 요청 모델과 reasoning override를 실제 지원하는지 확인하고, 모델 카탈로그나 지원 필드가 현재 작업 시작 뒤 바뀌었으면 해당 환경에서 변경사항을 반영할 수 있는 새 세션·재시작 등 절차를 거친 뒤 최소 점검으로 다시 확인한다.
- 위임 뒤에는 플랫폼이 제공하는 범위에서 요청 모델·실제 모델·입력/캐시/출력/추론 토큰·처리시간·상태를 확인한다. 실제 모델 ID나 토큰·처리시간을 노출하지 않는 환경에서는 요청값과 실행 상태만 기록하고 나머지는 `런타임 미노출`로 표시하며 추정하지 않는다. 미노출 표시는 공급자 확인을 대신하지 않는다. 개인정보·비공개 원문은 위임 전에 허용된 모델·공급자 경로를 확인할 수 있어야 하며, 확인되지 않으면 직접 처리한다. 결과의 실제 공급자가 승인 범위에 부합하는지 불명확하면 그 결과만으로 원문 판단을 확정하지 않는다. Luna 입력이 목표를 크게 넘거나 유사 문맥이 중복 전송되면 결과가 성공 상태여도 다음 위임 전에 분해와 모델 배정을 다시 설계한다.

#### 3.3.1 보조 모델 선택·호출과 새 세션 확인

GPT 경로에서 사용자가 하네스·팀 작업을 요청하면 3.1절로 분해 이점을 판단한 뒤 다음 순서로 실제 호출에 연결한다. 팀 요청만으로 모든 보조 작업을 주 모델에 일괄 상속시키거나, 반대로 병렬화 이점이 없는 작업까지 Luna에 위임하지 않는다.

1. **작업 기준으로 선택한다.** 사용자 지정 모델·공급자 선호를 현재 도구 정책과 자료 전송 허용 범위 안에서 우선 반영한다. 별도 지정이 없는 GPT 경로에서는 범위·입력·완료 기준이 명확하고 결과를 대사할 수 있는 작업에 `gpt-6-luna`를 우선한다. 제한된 관계 검토도 이 조건을 충족하면 Luna 후보이며, 최초 쟁점·결정적 예외·상충 해결·최종 통합은 주 모델이 맡는다. 별도 Sol 검토가 필요하면 5.2절의 기준과 이유를 적용한다.
2. **선택한 모델의 호출 경로를 확인한다.** 해당 모델에 연결된 적합한 프로필을 선택하거나, 허용되는 경우 현재 도구의 정확한 모델 ID와 지원 effort를 직접 지정한다. Luna를 선택했다면 `model: gpt-6-luna`는 현재 도구가 그 ID를 지원할 때만 사용하는 예시다. 모델 미지정은 환경의 기본 보조 설정 또는 부모 모델 상속으로 이어질 수 있으므로 Luna 선택을 보장하지 않는다. 도구가 모델 직접 지정에 사용자의 명시 요청을 요구하면, 이미 확인된 해당 모델 사용 요청·선호의 승인 범위 안에서만 지정한다. 승인이 없으면 상위 정책을 우선하고 모델 선택을 명시한 `prompts/run_harness_team.md`를 안내한다. 로컬 지침으로 도구 정책을 무효화하지 않는다.
3. **PC 설정은 Codex 로컬·프로젝트 설정을 사용하는 환경에서만 별도로 맞춘다.** 사용자 승인으로 GPT 보조 기본값을 바꾸는 경우 프로젝트 `.codex/config.toml`의 기본 보조 모델과 `.codex/agents/`의 실제 모델·effort·권한을 함께 확인한다. 상위 작업 모델이나 다른 공급자 프로필을 일괄 교체하지 않는다. 읽기 전용 작업자에게 수정을 맡기지 않고, 쓰기가 필요한 작업은 실제 쓰기 권한과 소유 범위를 갖춘 경로를 선택한다. 설정 백업과 새 세션 시험을 수행하며, PC별 설정·백업·시험자료는 공유 PR에 넣지 않는다. ChatGPT Work의 hosted 환경처럼 로컬 `.codex` 설정을 직접 노출·사용하지 않는 실행면에서는 해당 PC 설정 절차를 강제하지 않고, 현재 세션이 제공하는 모델·역할·도구·권한과 실제 실행 메타데이터로 확인한다.
4. **새 세션에서 실행을 확인한다.** 사용자에게 새 세션 시험을 요청받은 경우 같은 프로젝트의 새 채팅 또는 새 런타임 세션을 사용한다. 지원 모델·역할이 갱신됐는지 확인하고 비민감·작은 독립 과제를 실제 위임하여 입력 대사와 결과를 검증한다. 요청 모델, 호출 인수/선택 프로필, 생성·완료 상태와 실제 모델 메타데이터를 구분한다. 실제 모델이 노출되지 않으면 `런타임 미노출`로 남기며, 프로필 이름·자기보고·결과 품질만으로 실제 backend 모델이나 절감률을 단정하지 않는다. 실패하면 원인을 보완하고 실패 상태에서 성공한 것처럼 PR 검증을 보고하지 않는다.

역할 배정의 정본은 5.2절이다. 이 절은 비용·품질 후보를 추가하는 표가 아니라, 선택한 보조 모델의 배정이 실제 호출과 설정에 연결되는지 확인하는 절차다.

#### 3.3.2 실행환경별 호출 경로와 실패 처리

- 팀 작업에서 Luna·Grok·Flash 사용 요청은 **현재 실행환경의 서브에이전트 모델 선택 요청**으로 해석한다. Grok 모델 위임을 그록봇 MCP 호출로 해석하거나 자동 대체하지 않는다. 사용자가 그록봇 MCP·아르곤 등 별도 검토 경로를 명시한 경우에는 그 지정과 해당 도구·자료 전송 경계를 따른다.
- '적극 활용'은 모든 모델을 호출하라는 뜻이 아니다. 독립 작업의 시간·품질·사용량 이점, 자료 민감도와 현재 가용성으로 선택하고 역할을 고정하거나 불필요한 작업을 만들지 않는다.
- **Codex·OpenCodex·Work**: 현재 위임 도구에 노출된 정확한 모델 ID와 허용 인수·프로필만 사용한다. OpenCodex 전체 모델 목록, 주 모델 picker, 이전 세션의 지원 목록을 현재 서브에이전트의 호출 가능 목록으로 간주하지 않는다. hosted 환경에 로컬 설정 절차를 강제하지 않는다.
- **Hermes**: 현재 도구 스키마·설정과 coding 지침의 [하네스 2.1절](https://github.com/blue09040-afk/coding/blob/main/guides/AGENT_HARNESS.md#21-hermes-적용)을 따른다. Codex의 `spawn_agent`·`model`·fork 인수를 그대로 보내거나 per-task 모델 지정이 가능하다고 가정하지 않는다. CLI 작업자 경로는 해당 지침과 현재 권한 안에서만 사용한다.
- **호출 실패**: `Unknown model` 등 모델 ID·호출 인수 관련 오류가 발생하면 요청한 모델 ID·현재 도구의 지원 목록·실제 오류를 대조하고, 확인 범위의 호출 실패로 보고한다. 다른 ID나 경로가 확인되지 않으면 원인을 미확인으로 남기며 OpenCodex 전체의 미지원이나 모델 성능 문제로 확대하지 않는다. 지원 목록이나 설정이 갱신된 근거가 있을 때만 영향 범위를 다시 확인한다.
- 같은 조건으로 재시도하거나 별도 MCP·API·공급자 경로로 자동 우회하지 않는다. 현재 허용된 가용 모델 또는 주 에이전트 직접 처리로 이어가고 한계를 짧게 알린다. 실제 실행되지 않은 모델을 사용했다고 보고하지 않는다.

### 3.4 과거 OpenCodex 외부 패킷 워커 — 비활성 역사 경로

- 이 절에서 **비활성 역사 경로**로 관리하는 대상은 과거 `m1`에서 쓰던 **Gemini 전용 OpenCodex 외부 패킷 워커 경로**다. OpenCodex 프로젝트나 현재 runtime 전체를 삭제·금지 대상으로 정의하는 절이 아니다.
- 현재 `m1`에서 OpenCodex routed 모델을 사용할 때는 이 역사 경로를 적용하지 않는다. 실제 사용 가능 여부는 현재 runtime의 roster·surface·도구 지원과 `AGENTS.md`의 공급자·자료 경계를 기준으로 판단하며, xAI/Grok 전용 보정은 `guides/opencodex_grok_runtime.md`를 따른다.
- `guides/opencodex_external_worker_guide.md`, 관련 프롬프트와 도구는 로컬 운영본에만 보존하는 과거 운영·복구 근거다. GitHub `m1`과 공유 패키지에서는 제외하며, 현재 routed 모델 또는 네이티브 `spawn_agent`의 Luna·Terra 설정과 혼합하지 않는다.
- 이 **과거 외부 패킷 워커 경로 자체**를 재도입해야 할 때만 사용자의 별도 요청을 받은 뒤 현재 Codex 구성과의 충돌, 개인정보·외부 전송 경계, 백업·복구 계획을 먼저 재검토한다. 현재 OpenCodex runtime에서 이미 제공되는 routed 모델을 사용하는 것은 이 재도입 절차로 보지 않는다.

## 4. 실행 안내와 승인 경계

사용자의 명시적 요청 여부와 관계없이, 범위가 크거나 쓰기 작업이 포함된 병렬 작업을 시작할 때는 간단히 실행 방식을 알린다.

```text
요청을 병렬로 나누어 처리하겠습니다.

- 제가 직접 진행할 핵심 경로: ...
- 위임할 독립 작업: ...
- 파일 수정 범위: ...
- 통합 방식: ...
```

병렬 작업의 안내 자체를 승인 요청으로 사용하지 않는다. 재확인·필수 정보 부족·승인 필요 동작의 판단은 `AGENTS.md`의 `승인된 작업의 실행과 완료`를 따른다. 실제 샌드박스 권한 상승은 해당 도구의 승인 절차로 처리한다.

- 전체 설계 판단

- 서브에이전트 결과 검토
- 최종 답변 작성

### 5.2 모델·reasoning 수준 선택

2026-09-30 확인한 공식 [모델 선택 안내](https://learn.chatgpt.com/docs/model-selection), [GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna), [GPT-6.1 Sol](https://developers.openai.com/api/docs/models/gpt-6.1-sol) 문서를 기준으로 다음 역할을 사용한다. 아래 기본값은 이 저장소의 운영 후보이며 행정 업무에서의 성능 향상 실측 결과가 아니다. 현재 세션의 모델·위임 도구·지원 필드가 우선한다.

| 역할 | 현재 GPT 경로의 우선 후보 | 적용 기준 |
|---|---|---|
| 오케스트레이터 | 사용자가 선택한 주 모델. Sol 6.1이면 `gpt-6.1-sol` | 최초 쟁점·분해·결정적 원문 대조·최종 판단 |
| 범위가 명확한 보조 작업자 | `gpt-6-luna` | 추출·분류·대조·완전성 점검, 소유 범위가 정해진 수정·구현·도구 작업 |
| 제한된 관계·모순 검토자 | `gpt-6-luna`, `high / xhigh` 후보, 필요 시 `max` | 주 모델이 쟁점·자료 범위를 정했고 검증 가능한 보조 검토. 기존 Terra 역할을 우선 이 경로로 재배정 |
| 복합 관계·예외 검토자 | 주 모델 직접 처리 또는 별도 `gpt-6.1-sol` | 쟁점 설정부터 모호하거나 시점·권한·반대자료가 얽힌 판단. 별도 검토는 독립적 입력·관점의 실익이 있을 때만 |
| 난제 자문 | `gpt-6-astra` | `chatgpt_sol_external_review_harness.md`의 선택 게이트를 통과한 경우 |

- Sol 6.1을 사용하는 현재 GPT 경로의 기본 후보는 Luna 6·Sol 6.1·Astra다. GPT-5.6 Terra와 GPT-6 Sol은 기본 배정에서 제외하며, 제공된다는 이유나 검토 단계 수를 늘리기 위해 호출하지 않는다. 구형 모델의 명시적 비교 요청 또는 현재 후보로 충족하지 못하는 구체적인 호환성·가용성 조건이 있을 때만 예외를 검토한다. 모델 가용성이 없으면 자동으로 구형 후보를 되살리지 않고 현재 지원되는 경로를 확인하거나 직접 처리한다.
- GPT-6 Sol의 `none` 및 Chat Completions 도구 호출 지원 차이는 별도 API 구현의 호환성 조건이지 현재 Codex의 추가 검토자 역할 근거가 아니다. Sol 6.1을 별도 검토자로 쓰는 것은 같은 모델의 독립된 입력·관점 검토이며, 이전 Sol 6으로 나눠 호출해야 얻는 별도 성능 이점이 있다고 가정하지 않는다.
- **모델 선택과 reasoning effort는 별도로 판단한다.** Sol 6.1 API의 공식 지원 단계는 `low / medium / high / xhigh / max`이고 기본값은 `medium`이며 `none / minimal`은 지원하지 않는다. Codex·Work·routed 실행환경의 선택 단계와 실제 조정 기능은 그 환경에서 확인한다. 문서의 권고만으로 세션 설정이 바뀌었다고 보고하지 않는다.
- **Sol 6.1 운영 후보**는 단순 확인·형식 정리에 `low`, 일반 작성·관계 검토에 `medium`, 복잡한 법령 적용·상충 자료·오류 비용이 큰 최종 판단에 `high`다. 기존 작업에서 효과가 확인된 effort가 있으면 지원 범위 안에서 유지하고 대표 과제로 비교한다. `high`에서 남은 구체적 추론 문제에만 `xhigh / max` 등 실제 지원되는 상위 단계를 검토한다. 이 후보는 의무 하한·상한이나 검증된 최적값이 아니다.
- 입력 누락, 공식 원문 미확인, OCR·판독 실패, 도구·권한 제한은 effort를 높이기 전에 원인을 보완한다. 다문서라는 이유만으로 Luna에서 승격하지 않는다. 쟁점이 위임 범위를 벗어나거나 결정적 예외·상충을 보조 검토로 해소하지 못하면 주 모델이 직접 대조하고, 독립 검토의 실익이 있으면 별도 Sol 6.1을 사용한다.
- **Astra 운영 후보**는 범위를 좁힌 자문에 `low~medium`, 반론·다단계 추론이 남으면 `high` 이상의 실제 지원 단계다. 중요하다는 이유만으로 자동 호출하거나 최고 effort를 고정하지 않고, 반대로 `medium` 같은 절대 상한도 두지 않는다.
- 같은 모델을 별도 검토자로 쓰더라도 입력·평가 관점과 근거 대조를 독립시킨다. 같은 모델의 동의를 이종 모델 교차검증이나 결론의 확정 근거로 표현하지 않는다.
- API의 multi-agent·async tool calling·중간 effort 변경 지원을 Codex 앱의 현재 도구 지원으로 간주하지 않는다. 실제 위임 도구가 없으면 주 모델이 직접 처리한다. API 호출 구현을 변경하는 별도 작업에서는 Responses 도구 호출과 매개변수 호환성을 공식 문서로 확인한다.
- Gemini·Grok 등 다른 공급자의 roster·ID는 현재 runtime과 `AGENTS.md`의 공급자·자료 경계로 확인한다. 모델 전환·fallback은 개인정보 전송 승인이나 현재 파일·셸·GitHub 권한을 확대하지 않는다.
- 모델별 사용 비율·에이전트 수를 고정하지 않는다. 역할을 나누는 이점이 위임·인계·통합·재검증 비용보다 큰 경우에만 사용한다.

#### 5.2.1 가격·사용량 기준과 해석

- GPT-5.6의 과거 크레딧 단가와 `25:1 / 10:1 / 2.5:1` 배율을 현재 모델의 비용 판단에 적용하지 않는다. 구독·크레딧 경로는 공식 [Codex·Work 가격과 사용량](https://learn.chatgpt.com/docs/pricing), API 경로는 공식 [API 가격](https://developers.openai.com/api/docs/pricing)을 확인한다. 확인일과 실제 모델·요금 경로를 구분한다.
- API 토큰 가격을 구독 잔여량·작업 가능 횟수로 환산하지 않는다. 실제 사용량은 입력·캐시·출력·추론·도구 결과·컨텍스트 길이·속도 설정에 따라 달라진다. 계정 잔여량과 토큰이 노출되지 않으면 추정하지 않는다.
- 단가 비교가 필요하면 같은 종류의 토큰과 처리 조건으로 계산하고, `Sol 1회 = Luna N회`처럼 호출 횟수 비율로 고정하지 않는다. 변동 가격표를 실행 규칙으로 복제하기보다 작업 시점의 공식 안내를 확인한다.

#### 5.2.2 품질 보존형 라우팅

- **자료 완전성 경로**: 주 모델이 자료·패킷·스키마를 확정한다 → 가용한 반복 작업자가 처리한다 → 입력 수와 처리 상태를 대사한다 → 오류 비용과 남은 불일치가 정당화하는 경우 독립 재검증한다 → 모호성·충돌만 검토자 또는 주 모델이 해결한다 → 주 모델이 결정적 원문과 최종 결과를 확인한다.
- **판단·종합 경로**: 주 모델이 쟁점과 판단 경계를 정한다 → 위임 이점이 있으면 가용한 관계·예외 검토자가 근거 중심 보조 검토를 한다 → 주 모델이 충돌과 결정적 원문을 대조하고 최종 통합한다.
- 독립 재검증에는 1차 결론을 먼저 보여 주지 않고 같은 자료 범위·평가 기준을 전달한다. 단순 동의 여부보다 누락·상이한 근거·상충 결과를 비교한다.

### 5.3 서브에이전트에 위임하기 좋은 일

| 에이전트 유형 | 적합 작업 |
|---|---|
| explorer | 특정 코드 경로, 테스트 구조, API 사용 위치 조사 |
| worker | 소유 범위가 명확하고 다른 작업과 충돌하지 않는 구현·수정 |

위임에는 목적·범위·기대 결과와 읽기/쓰기 소유권을 명확히 전달한다. 기본 지침에 이미 있는 공통 금지사항은 그대로 상속하고 매번 복제하지 않는다. 작업에 특유한 공급자·자료·수정 제한, 충돌·미확인 사항과 근거 위치만 추가한다. 대량·누락 민감형 작업에는 입력별 처리 상태와 완전성 대사를 요구한다.

## 8. 검증 루프

복합 산출물은 다음 루프로 검증한다.

```text
초안 작성
  -> 결함 점검
  -> 필요한 문단만 수정
  -> 테스트 또는 근거 재확인
  -> 최종 통합
```

검증의 범위는 변경·오류 위험에 맞춘다. 필요한 근거·형식·관련 기능 검증이 통과하고 실질적 미해결 문제가 없으면 최종 통합으로 진행한다. 같은 검증을 확대·반복하는 것은 새 변경, 실패, 남은 불확실성 또는 사용자의 반복 검토 요청이 있을 때로 한정한다. 행정 사건의 검토 검증과 작성 후 일치 점검은 `document-validation-pipeline`을 정본으로 따른다.

검증은 다음 위험에 집중하고 해당 없는 항목은 적용하지 않는다.

- 핵심 근거·반대자료·예외·시점·권한의 누락 또는 결론의 과장
- 변경 범위의 기능·형식 오류와 기존 작업의 훼손
- 개인정보·외부 전송·쓰기 소유권의 경계 위반
- 위임한 입력·처리 상태·근거 위치의 불일치와 과대한 문맥 중복

누락 민감형 작업은 `입력 자료 수 = 처리 완료 + 제외(사유) + 미확인 + 판독 불가`를 대사한다. 모델 동의만으로 통과시키지 않으며, 불일치가 해소되지 않으면 검토자 또는 주 모델이 결정적 원문을 직접 확인한다. 결함코드·전체 점검표는 자동 산출물이 아니다.

## 11. 종료·인수인계

최종본을 혼동할 우려가 있거나 다음 작업자에게 이어질 미완료 판단이 있으면 기준 파일·완료 상태·남은 작업·필요 원문 위치를 남긴다. 작성 기준은 `../prompts/create_handoff.md`, 행정 작업의 기록 적용 조건은 `BASE_INSTRUCTIONS.md` 45-3을 따른다.

- 단순 답변·소규모 수정의 종료만으로 폴더 이동·정리 로그·HANDOFF를 자동 생성하지 않는다.
- 사건 종료·교체를 수행하는 경우 해당 사건 스킬의 보존·검증 절차를 따른다.
- 필요한 정리는 삭제보다 보존을 우선하고, 이동 전후 경로·충돌 여부를 확인한다. 파일을 옮기면 기존 인수인계의 실제 경로도 맞춘다.
- 공통 지침 저장소에서 사건 종료 양식을 기계적으로 적용하지 않는다.
