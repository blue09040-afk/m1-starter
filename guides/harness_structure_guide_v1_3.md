# 서브에이전트 병렬 작업 구조 운용 지침

> **문서 버전**: v2.16  
> **개정일**: 2026-08-30  
> **파일명 안내**: `harness_structure_guide_v1_3.md`는 기존 프롬프트와 사건 폴더의 참조 호환을 위해 유지한다. 현재 적용 버전은 이 문서의 `문서 버전`을 기준으로 판단한다.  
> **적용 범위**: Codex 및 Work 등 현재 세션에서 서브에이전트 위임 기능이 실제로 제공되는 환경에서 복합 태스크를 분석·분해·위임·검증할 때  
> **핵심 원칙**: 하네스는 항상 적용하는 절차가 아니다. 서브에이전트 사용은 현재 세션 정책과 도구 가용성을 우선하며, 독립적이고 범위가 명확한 작업에서 실질적인 속도 또는 검증 이점이 있을 때 적용한다.

---

## 1. 개념 정의

**하네스 적용 판단** = 요청을 바로 실행하기 전에 작업 단위, 산출물, 로그, 검증 흐름을 별도로 설계할 필요가 있는지 판단하는 단계.

**병렬 작업 구조** = 본 에이전트 1개가 오케스트레이터 역할을 맡고, 필요 시 독립적인 서브에이전트가 제한된 하위 작업을 병렬로 수행하는 구조.

오케스트레이터는 다음을 책임진다.

- 요청 목적과 제약 파악
- 태스크 분해
- 직접 처리할 핵심 경로와 위임 가능한 보조 경로 구분
- 서브에이전트 지시문 작성
- 결과 검토·통합
- 최종 산출물 품질 확인

서브에이전트는 본 에이전트를 대체하지 않는다. 최종 판단, 파일 반영, 사용자 보고 책임은 오케스트레이터에게 있다.

---

## 2. 하네스 적용 판단

하네스 지침은 다음 경우에 먼저 확인한다.

- 사용자가 `하네스`, `팀 작업`, `병렬`, `나눠서`, `여러 에이전트`, `대량`, `반복`, `여러 산출물`, `다음 대화방에서 이어서`를 언급한 경우
- 산출물이 2개 이상이고 서로 다른 검토 흐름이 필요한 경우
- 대량 파일, 대량 행, 여러 부서 자료처럼 누락 위험이 큰 경우
- 다른 대화방이나 다른 컴퓨터에서 이어갈 가능성이 있어 로그 또는 인수인계가 필요한 경우

다음 경우에는 하네스 없이 진행할 수 있다.

- 단일 문안 수정
- 짧은 검토 의견 작성
- 파일 1~2개 확인 후 답할 수 있는 작업
- 단순 오탈자 또는 표현 정리
- 사용자가 이미 작업 순서를 명확히 준 경우

하네스를 적용하더라도 항상 서브에이전트를 쓰는 것은 아니다. 서브에이전트 없이도 작업 단위, 로그, 산출물, 검증 흐름만 간단히 설계할 수 있다.

---

## 3. 병렬 구조 사용 조건

서브에이전트 위임을 지원하는 환경에서는 병렬 에이전트를 기계적으로 사용하지 않는다. 아래 조건을 모두 만족할 때 사용한다.

1. 현재 세션의 상위 실행정책과 사용 가능한 도구가 서브에이전트 사용을 허용한다.
2. 하위 작업이 구체적이고 범위가 명확하며 서로 독립적이다.
3. 병렬화가 실제 처리시간을 줄이거나 교차검증 품질을 높인다.
4. 같은 파일이나 같은 판단 지점을 동시에 수정하지 않으며, 본 에이전트가 결과를 검토·통합할 수 있다.

사용자가 "서브에이전트", "위임", "병렬 에이전트", "여러 에이전트로 나눠서"라고 요청한 경우는 적극적인 적용 신호이지만 필수 조건은 아니다. 서브에이전트 사용은 사용자가 허용한 범위나 외부 변경 권한을 확대하지 않는다.

### 3.1 Sol 분해 위험 게이트

업무 분해 여부와 분해 단위는 Sol 오케스트레이터가 직접 결정하며 하위 모델에 위임하지 않는다. 위임 전에는 다음을 먼저 확인한다.

- 결론이 여러 문서의 관계, 예외·경과규정, 시점, 권한 또는 반대자료에 따라 달라지는가
- 각 하위 과제를 다른 결과 없이 독립적으로 검증할 수 있고, 누락도 발견할 수 있는가
- 근거 위치와 미확인·충돌 자료를 인계할 수 있는가
- 위임·인계·재검증 비용이 Sol의 직접 처리보다 실질적으로 작은가

첫 항목에 해당하거나 나머지를 충족하지 못하면 `분해 위험 업무`로 본다. 이때는 문서별로 결론을 나누지 않고 Sol이 최초 쟁점과 핵심 맥락을 유지하며, 서브에이전트에는 추출·탐색·모순 점검 같은 역할만 맡긴다. 최종 판단 전에는 Sol이 결정적 원문을 직접 대조한다. 비용 절감은 Sol의 판단을 대체하는 것이 아니라 반복 탐색·형식 작업을 줄이는 방식으로 달성한다.

적합한 예시는 다음과 같다.

| 유형 | 예시 |
|---|---|
| 독립 코드 영역 분석 | 프론트엔드 상태 관리와 백엔드 API 라우팅을 별도로 조사 |
| 독립 파일군 수정 | 충돌 없는 모듈 A/B를 각각 수정 |
| 교차 검토 | 구현 중 본 에이전트가 진행하고, 서브에이전트가 테스트 실패 원인만 조사 |
| 대량 자료 분류 | 서로 의존하지 않는 문서 묶음을 기준별로 나누어 정리 |

직접 처리해야 하는 경우는 다음과 같다.

- 하위 과제의 범위와 기대 산출물을 명확히 나누기 어려운 경우
- 다음 단계가 바로 특정 조사 결과에 막혀 있는 경우
- 하위 작업이 같은 파일을 동시에 수정해야 하는 경우
- 예상 서브에이전트 수가 1개뿐이고 병렬 이점이 작은 경우
- 사용자가 빠른 단일 답변을 요구한 경우

### 3.2 자료 처리·승인·컨텍스트 경계

- PDF·HWPX 원본과 로컬 추출본을 읽는 기본 경로에서는 개인정보 마스킹을 자동 실행하지 않는다. 마스킹은 사용자 또는 적용 작업 프로필이 명시한 경우에만 수행한다.
- 마스킹이 필요한 경우에는 실행 전에 대상, 적용 범위, 원본·추출본·산출물 중 적용 위치를 확인한다. 담당 직원 성명·업무 연락처 등 업무 수행·검증에 필요한 정보는 사용자가 허용하거나 작업 프로필이 정한 범위에서 보존할 수 있다. 원본에 이미 존재하는 마스킹·가림 정보는 추정·복원·전사하지 않는다.
- AI 자동 실행은 GUI·BAT보다 설치 스킬의 안정된 PowerShell 래퍼를 우선한다. 텍스트 PDF의 AI 검토용 마스킹은 `run_repo_pdf_to_md.ps1 -MaskPii`, 스캔 PDF·이미지는 `run_repo_pdf_utility.ps1 -Tool oneocr-mask`의 `masked-text` 또는 `visual-mask`, HWPX 추출은 `read_hwpx_text.ps1 -MaskPii`를 사용한다. 각 스위치가 없으면 비마스킹 기본 경로를 유지한다.
- 개인정보·민감정보·비공개 자료 원문은 모델 위임이 허용된 경우에도 GPT 모델(Luna·Terra·Sol)에만 맡긴다. Gemini 등 다른 공급자 모델이 꼭 필요하면 최소 범위로 마스킹·검증한 뒤 대상·서비스·목적을 알리고 명시 승인을 받는다.
- 외부 OCR·변환과 병렬 위임은 승인 범위를 확대하지 않으며, 마스킹은 외부 전송 승인을 대신하지 않는다.
- 위임 전에는 작업별 `최소 충분 컨텍스트`를 정한다. 관련 최신 대화, 직접 필요한 파일·쪽·절, 확인된 사실과 미확인 쟁점만 전달하되, 결론을 바꿀 반대자료·예외·시점 정보까지 줄여서는 안 된다. 전체 대화·전체 저장소·불필요한 원문은 관성적으로 fork하거나 다시 읽지 않는다.
- 다문서·고위험 작업은 자료 식별자별로 `읽음 / 사용 / 제외(사유) / 미확인 / 판독 불가`를 기록해 누락을 확인한다. 소규모·저위험 작업에는 이 대장을 기계적으로 만들지 않는다.
- 오케스트레이터는 조사 항목, 담당 에이전트, 확인 근거, 완료 상태를 짧게 기록한다. 서브에이전트 결과는 확인 사실, 근거 위치, 충돌 자료, 미확인 범위와 확신도 중심으로 받아 통합하며, 요약만으로 고위험 결론을 승인하지 않는다.

### 3.3 내장 서브에이전트 컨텍스트·동시성 게이트

- 내장 `spawn_agent`는 `fork_turns="none"` 또는 필요한 최근 턴만 넘기는 최소 fork를 기본으로 한다. 전체 대화 상속은 Terra·Sol이 장기 맥락을 직접 유지해야 하고 중복 비용보다 검증 이점이 큰 예외에만 사용하며, 이유를 남긴다.
- Luna는 운용상 범위가 명확한 leaf worker로 취급한다. 독립된 추출·분류·대조·형식 정리·체크리스트처럼 반복 가능하고 결과를 대사할 수 있는 작업에 사용하며, 파일 수정·복합 도구 사용·다문서 관계 판단은 Terra `medium` 이상으로 맡긴다.
- 누락 민감형 Luna 작업은 `high` reasoning을 기본값으로 명시한다. `low`는 결과를 규칙으로 완전히 대사할 수 있는 기계적 형식 변환에만 쓰고, `max`는 범위가 제한되고 평가 기준이 분명한 최난도 품질 우선 패킷에서 대표 과제로 효과를 확인한 뒤 선택한다. reasoning을 높이면 복합 논리·가정·예외 점검의 열화를 줄일 수 있지만, 전달되지 않은 자료·잘못된 분해·불완전한 OCR·추출 실패·출력 잘림을 복원할 수는 없다.
- Luna의 예상 입력은 20,000토큰 이하를 목표로 한다. 이를 넘을 가능성이 있으면 패킷을 줄이거나 Terra `medium` 이상으로 승격한다.
- 같은 대화의 Luna 실행은 필요한 최소 수부터 사용한다. 패킷이 작고 경계가 분명하며 대형 공통 문맥을 중복하지 않는 독립 작업은, 병렬화가 시간 단축 또는 교차검증 품질 향상에 실질적으로 기여하고 그 이점이 위임·인계·통합·재검증 비용을 상회할 때에만 현재 실행환경이 허용하는 범위에서 병렬화한다. 저장소 자체에서는 모델별 또는 고정된 동시 실행 상한을 두지 않으며, 상위 실행정책과 실제 세션·도구 제한, 런타임이 허용·배정한 가용 동시성, 단일 쓰기 소유권을 우선한다. 추가 병렬 웨이브의 한계효용이 작아지면 더 생성하지 않는다.
- 프로필 선택을 지원하는 로컬 Codex 구성에서는 `luna_worker`(Luna-high·읽기 전용)와 `terra_reviewer`(Terra-medium·읽기 전용)를 사용하고, 모델 미지정 일반 보조 작업의 프로젝트 기본값은 Terra-medium으로 둔다. 현재 확인한 Work Mode에서는 프로필 선택 필드 대신 `model`·`reasoning_effort` 직접 지정이 가능했다. 일반적으로는 프로필 선택 필드가 없더라도 현재 도구가 해당 직접 지정 필드를 실제 지원하는 경우에만 정확한 모델 식별자와 추론 수준을 지정하고, 직접 지정 기능도 없으면 지원되지 않는 필드를 가정하지 않는다.
- 주 에이전트의 모델 선택이 서브에이전트 모델을 자동으로 보장한다고 간주하지 않는다. 위임 전에 현재 도구가 요청 모델과 reasoning override를 실제 지원하는지 확인하고, 모델 카탈로그나 지원 필드가 현재 작업 시작 뒤 바뀌었으면 해당 환경에서 변경사항을 반영할 수 있는 새 세션·재시작 등 절차를 거친 뒤 최소 점검으로 다시 확인한다.
- 위임 뒤에는 플랫폼이 제공하는 범위에서 요청 모델·실제 모델·입력/캐시/출력/추론 토큰·처리시간·상태를 확인한다. 현재 확인한 Work Mode처럼 실제 모델 ID나 토큰·처리시간을 노출하지 않는 환경에서는 요청값과 실행 상태만 기록하고 나머지는 `런타임 미노출`로 표시하며 추정하지 않는다. Luna 입력이 목표를 크게 넘거나 유사 문맥이 중복 전송되면 결과가 성공 상태여도 다음 위임 전에 분해와 모델 배정을 다시 설계한다.

### 3.4 OpenCodex 외부 워커 — 비활성 역사 경로

- OpenCodex는 2026-08-18 현재 삭제된 경로이므로 하네스가 실행·자동 시작·재설치하거나 외부 워커로 위임하지 않는다.
- `guides/opencodex_external_worker_guide.md`, 관련 프롬프트와 도구는 로컬 운영본에만 보존하는 과거 운영·복구 근거다. GitHub `m1`과 공유 패키지에서는 제외하며, 네이티브 `spawn_agent`의 Luna·Terra 설정과 혼합하지 않는다.
- 재도입이 필요하면 사용자의 별도 요청을 받은 뒤 현재 Codex 구성과의 충돌, 개인정보·외부 전송 경계, 백업·복구 계획을 먼저 재검토한다.

## 4. 사용자 확인 문구

사용자의 명시적 요청 여부와 관계없이, 범위가 크거나 쓰기 작업이 포함된 병렬 작업을 시작할 때는 간단히 실행 방식을 알린다.

```text
요청을 병렬로 나누어 처리하겠습니다.

- 제가 직접 진행할 핵심 경로: ...
- 위임할 독립 작업: ...
- 파일 수정 범위: ...
- 통합 방식: ...
```

별도 허락이 필요한 경우는 다음과 같다.

- 네트워크 접근, 패키지 설치, 외부 서비스 호출 등 권한 상승이 필요한 작업
- 파괴적 작업 또는 되돌리기 어려운 파일 이동·삭제
- 사용자가 지시하지 않은 대규모 리팩터링

## 5. 역할 배분 원칙

### 5.1 오케스트레이터가 직접 해야 할 일

- 업무 분해 가능 여부와 분해 단위 결정
- 분해 위험 업무의 최초 쟁점 설정과 결정적 원문 대조
- 즉시 다음 단계에 필요한 차단 작업
- 전체 설계 판단
- 사용자 요구사항 해석
- 최종 파일 수정 방향 결정
- 서브에이전트 결과 검토
- 최종 답변 작성

### 5.2 모델·reasoning 수준 선택

위임에는 현재 도구에서 실제 사용 가능한 모델만 배정하고, 작업 난도에 필요한 최소 reasoning을 사용한다.

| 모델 | 우선 역할 | 자료 경계 |
|---|---|---|
| Gemini Flash | 비활성 역사 경로(OpenCodex 삭제) | 호출 금지 |
| Gemini Pro | 비활성 역사 경로(OpenCodex 삭제) | 호출 금지 |
| Luna | 범위가 명확한 대량 추출·분류·대조·완전성 점검 | GPT 허용 범위 |
| Terra | 모호성·문서 간 관계·도구 사용이 있는 중간 난도 작성·검토 | GPT 허용 범위 |
| Sol | 지휘·고위험 판단·충돌 해결·최종 검증 | GPT 허용 범위 |

- 판단·종합 경로는 `Sol 오케스트레이터 + Terra-medium 내장 서브에이전트`를 우선한다. 누락 민감형 반복 작업은 3.3의 게이트를 통과한 `Luna-high`를 우선하고, 모델과 reasoning을 위임 시 명시한다.
- Gemini Flash·Pro의 기존 OpenCodex 외부 패킷 경로는 비활성이다. 현재 하네스는 이를 호출하거나 대체 경로로 사용하지 않으며, 재도입은 3.4의 별도 검토를 거친다.
- Luna `high`는 추론·검증 과정에서 생길 수 있는 누락을 줄이기 위한 품질 보존 설정이지, 불완전한 입력을 보충하는 수단이 아니다. Luna `max`는 더 높은 reasoning의 품질 이득을 대표 과제에서 확인할 수 있고 추가 토큰·지연을 감수할 가치가 있을 때만 사용한다.
- 모호한 지시, 문서 간 의존관계, 결론을 바꾸는 예외·반대자료, 복합 도구 사용, 파일 수정이 있으면 Terra `medium`을 우선한다. 복잡한 독립 검토에는 Terra `high`, 최종 판단과 충돌 해결에는 Sol을 사용한다.
- 실패·근거 부족·결론 불명확·독립 검증 불일치가 있으면 `Luna → Terra-medium`, `Terra → 독립 Sol` 순으로 승격하고, 메인 Sol이 최종 통합한다.
- 위임 후 요청 모델과 플랫폼이 노출하는 경우 실제 사용 모델을 확인한다. 실제 모델이 미노출이면 요청값만 기록하고 확인했다고 단정하지 않는다. 모델을 대체하더라도 민감자료의 공급자 경계는 바꾸지 않는다.
- 모델별 사용 비율이나 에이전트 수를 고정하지 않는다. Sol이 해야 할 판단을 유지한 채 반복 탐색·분류·형식 작업만 적합한 모델에 위임하고, 절감 효과는 실제 크레딧·토큰과 품질 검증 결과로 판단한다.

#### 5.2.1 크레딧 기준과 해석

2026-08-18 확인한 OpenAI 공식 [Codex 가격·사용량 안내](https://learn.chatgpt.com/docs/pricing)의 100만 토큰당 크레딧 단가는 다음과 같다.

| 모델 | 입력 | 캐시 입력 | 출력 |
|---|---:|---:|---:|
| GPT-5.6 Sol | 125 | 12.5 | 750 |
| GPT-5.6 Terra | 50 | 5 | 300 |
| GPT-5.6 Luna | 5 | 0.5 | 30 |

- 같은 입력·캐시 입력·출력 토큰 구성이라면 `Sol:Luna = 25:1`, `Terra:Luna = 10:1`, `Sol:Terra = 2.5:1`이다. 따라서 Luna에 더 높은 reasoning이나 독립 재검증을 일부 사용해도 전체 사용량을 줄일 여지가 있다.
- 이 비율은 호출 횟수 비율이 아니라 같은 종류의 토큰에 대한 단가 비율이다. 실제 크레딧과 주간 사용량은 컨텍스트 크기, reasoning, 도구 결과, 출력 길이, 캐시와 속도 설정에 따라 달라지므로 `Sol 1회 = Luna 25회`로 고정 계산하지 않는다.
- 가격·사용량 기준은 변동 정보이므로 큰 작업을 설계하거나 비율을 개정할 때 공식 안내의 확인일과 최신 단가를 다시 확인한다.

#### 5.2.2 품질 보존형 라우팅

- **자료 완전성 경로**: Sol이 자료 목록·패킷·출력 스키마를 확정한다 → Luna-high가 1차 추출·분류·대조를 수행한다 → 입력 수와 처리 상태를 기계적으로 대사한다 → 중요하거나 오류 비용이 큰 경우 별도 Luna-high가 독립 재검증한다 → 불일치·모호성만 Terra-medium으로 승격한다 → Sol이 결정적 원문과 최종 결과를 확인한다.
- **판단·종합 경로**: Sol이 쟁점과 판단 경계를 정한다 → Terra-medium이 문서 간 관계·예외·도구 사용이 필요한 보조 검토를 수행한다 → Terra 결과가 복잡하거나 충돌하면 Sol이 직접 원문을 대조하고 최종 판단한다.
- Luna를 두 번 쓰는 경우 2차 에이전트에는 1차 결론을 먼저 보여 주지 않고 같은 범위·스키마로 독립 판단하게 한다. 단순 동의 여부가 아니라 누락·상이한 근거·상충 결과를 비교한다.

### 5.3 서브에이전트에 위임하기 좋은 일

| 에이전트 유형 | 적합 작업 |
|---|---|
| explorer | 특정 코드 경로, 테스트 구조, API 사용 위치 조사 |
| worker | 소유 범위가 명확하고 다른 작업과 충돌하지 않는 구현·수정 |

위임 지시문에는 반드시 다음을 포함한다.

- 작업 목적
- 읽거나 수정할 파일·모듈 범위
- 건드리지 말아야 할 범위
- 기대 산출물
- 기존 변경을 되돌리지 말라는 지시
- 코드 변경 시 변경한 파일 목록 보고 지시
- 읽기 컨텍스트와 쓰기 소유권: 필요한 자료 범위만 지정하고, 파일별·판단 지점별 단일 담당자를 명시
- 근거 위치, 충돌·미확인 자료, 판독하지 못한 범위와 확신도 보고
- 민감도·허용 모델·마스킹 및 승인 여부, 요청 모델·reasoning, 플랫폼이 노출하는 경우 실제 사용 모델 확인과 미노출 값 보고
- 입력 자료 식별자별 `처리 완료 / 제외(사유) / 미확인 / 판독 불가` 상태와 근거 위치
- 누락 민감형 작업의 완전성 대사식: `입력 자료 수 = 처리 완료 + 제외(사유) + 미확인 + 판독 불가`

## 6. 코드 작업 분해 기준

코드베이스 작업은 다음 순서로 판단한다.

1. 저장소 구조와 관련 파일을 먼저 읽는다.
2. 핵심 경로와 보조 경로를 구분한다.
3. 파일별·겹치는 판단 지점별로 단일 쓰기 담당자를 정해 같은 파일이나 같은 판단 지점을 여러 에이전트가 동시에 수정하지 않도록 한다.
4. 본 에이전트는 통합에 필요한 공통 인터페이스와 테스트 기준을 유지한다.
5. 서브에이전트 결과가 돌아오면 변경 파일을 검토한 뒤 필요한 보완만 한다.

위임 가능한 예시는 다음과 같다.

| 상황 | 분해 방식 |
|---|---|
| UI와 API가 분리된 기능 | 본 에이전트가 API 계약 확정, worker가 UI 구현 |
| 테스트 실패 다수 | 본 에이전트가 구현 수정, explorer가 실패 로그와 원인 조사 |
| 문서와 코드 동시 갱신 | 본 에이전트가 코드 수정, worker가 문서 갱신 |
| 독립 모듈 2개 수정 | worker별로 모듈 소유권을 명확히 분리 |

## 7. 조사·법령·최신 정보 처리

법령, 가격, 일정, 표준, 라이브러리 버전, 최신 정책처럼 변동 가능성이 있는 정보는 반드시 현재 출처를 확인한다.

처리 원칙은 다음과 같다.

- 공식 문서, 원문, 법령·판례 원문을 우선한다.
- 요약 블로그나 2차 자료만으로 결론을 내리지 않는다.
- 날짜, 시행일, 버전, 적용 범위를 명시한다.
- 불확실한 항목은 `[확인 필요]`로 남긴다.
- 사용자가 특정 출처나 파일을 준 경우 그 내용을 우선 읽는다.

법령·행정 문서 작업에서는 다음 게이트를 둔다.

| 단계 | 다음 단계 진행 조건 |
|---|---|
| 쟁점 정리 | 주장, 확인된 사실, 추론을 구분했다 |
| 자료 확인 | 원문 출처와 날짜를 확보했다 |
| 법령 확인 | 조문명, 조문번호, 시행일을 확인했다 |
| 초안 작성 | 확인된 사실과 원문 근거 밖의 내용을 추가하지 않았다 |
| 최종 검토 | 개인정보, 관할, 권한, 절차, 표현 수위를 점검했다 |

## 8. 검증 루프

복합 산출물은 다음 루프로 검증한다.

```text
초안 작성
  -> 결함 점검
  -> 필요한 문단만 수정
  -> 테스트 또는 근거 재확인
  -> 최종 통합
```

검증 기준은 다음과 같다.

- 업무가 잘못 분해되어 문서 간 관계나 쟁점이 빠지지 않았는가
- 다문서·고위험 작업의 자료 처리 범위와 미확인 자료가 드러나는가
- 결정적 사실·조문·예외·시점·반대자료를 Sol이 원문에서 직접 확인했는가
- 사실과 추론이 구분되어 있는가
- 날짜, 버전, 시행일, 수치가 맞는가
- 출처 없는 단정이 없는가
- 요청 범위를 넘는 판단이 없는가
- 기존 코드·문서 스타일과 맞는가
- 테스트 또는 합리적 대체 검증을 수행했는가
- 사용자 또는 다른 작업자가 만든 기존 변경을 되돌리지 않았는가
- 경량 모델에 과대한 전체 대화가 전달되거나 같은 공통 문맥이 병렬 에이전트마다 중복되지 않았는가
- 요청 모델과 실행 상태를 확인하고, 플랫폼이 노출하는 경우 실제 모델·입력/캐시/출력/추론 토큰·처리시간을 기록했는가. 미노출 값은 추정하지 않고 모델 승격 또는 재설계 필요성을 판정했는가
- 입력 자료 수와 처리 상태 합계가 일치하고 각 결과에 근거 위치가 있는가
- 높은 reasoning을 불완전한 컨텍스트·추출 실패·잘못된 분해의 대체 수단으로 사용하지 않았는가
- 독립 Luna 재검증 결과가 다르면 차이를 해소하거나 Terra·Sol로 승격했는가

결함 코드는 필요할 때만 사용한다.

| 코드 | 유형 | 내용 |
|---|---|---|
| F1 | 사실 불명확 | 근거 없이 사실로 단정 |
| F2 | 원문 부재 | 원문·출처 없이 요약만 존재 |
| F3 | 시점 오류 | 날짜·버전·시행일 불일치 |
| F4 | 범위 과잉 | 요청 범위를 넘는 조사·판단 |
| F5 | 표현 과확장 | 근거보다 강한 표현 |
| F6 | 주체 불명확 | 누가 무엇을 했는지 불분명 |
| F7 | 절차 누락 | 필요한 후속 절차·권한·기한 누락 |
| F8 | 개인정보 위험 | 불필요한 식별 정보 노출 |
| F9 | 기존 내용 충돌 | 기존 회신·문서·코드 동작과 충돌 |
| F10 | 위임 경계 위반 | 민감 원문을 허용되지 않은 모델·서비스로 전달 |
| F11 | 분해·인계 누락 | 잘못된 분해 또는 인계로 쟁점·근거·반대자료·미확인 범위가 누락 |
| F12 | 컨텍스트·동시성 과부하 | 경량 모델에 과대 문맥을 전달하거나 같은 공통 문맥을 중복 병렬 호출 |
| F13 | 완전성 대사 실패 | 입력·처리 상태 수가 맞지 않거나 근거 위치가 빠지고 독립 검증 불일치가 해소되지 않음 |

## 9. 통합 및 사용자 보고

최종 답변은 사용자가 바로 판단할 수 있게 작성한다.

기본 순서는 다음과 같다.

1. 처리 결과
2. 변경한 파일 또는 산출물
3. 검증한 내용
4. 남은 위험 또는 못 한 작업
5. 필요한 다음 단계

코드 변경 작업에서는 파일 경로와 테스트 결과를 반드시 포함한다. 테스트를 실행하지 못했으면 이유를 명시한다.
서브에이전트의 실제 모델이 확인 가능하고 요청과 다르거나 공급자 대체가 있었으면 함께 알린다. 실제 모델이 미노출이면 요청 모델과 미노출 사실을 구분해 알린다.

## 10. 업무 유형별 권장 구조

### A. 코드 수정

- 본 에이전트: 요구사항 해석, 핵심 설계, 통합, 최종 검증
- worker: 독립 파일 또는 모듈 단위 구현
- explorer: 관련 코드 위치, 테스트 구조, 회귀 위험 조사

### B. 문서 정리

- 본 에이전트: 최종 문서 톤과 구조 결정. 문서 간 관계가 결론에 영향을 주면 먼저 공통 쟁점 지도를 유지한다.
- Luna-high worker: 자료별 추출·분류·표 정리·누락 대장처럼 범위와 대사 기준이 명확한 작업
- Terra-medium worker: 문서 간 관계를 종합하거나 모호한 표현·예외를 판단하는 독립 섹션 초안
- 통합 시 중복, 용어, 날짜, 출처를 정리한다.

### C. 법령·행정 검토

- Sol 오케스트레이터: 최초 쟁점 설정, 핵심 사실·공식 출처 확인, 결정적 원문 대조와 최종 판단
- Luna-high explorer/worker: 특정 법령·판례·내부 문서의 위치, 자료별 근거 목록, 연표, 형식화된 모순·누락 대장을 독립적으로 작성
- Terra-medium explorer/worker: 문서 간 관계, 예외, 상충 자료와 조건부 적용을 독립적으로 검토
- 결론은 서브에이전트 요약만으로 승인하지 않고 원문 조문과 적용 시점을 기준으로 조건부 표현을 사용한다.

### D. 교차 검증

사용자가 교차 검증을 요청하면 다음 형식으로 점검한다.

```text
[타당] 근거가 충분한 주장
[오류/과장] 사실 오류, 근거 부족, 논리 비약
[확인 필요] 판단 보류 또는 추가 확인 필요
[보완 항목] 이번 라운드에서 수정할 사항
```

## 11. 세션 종료 전 정리

대량 자료 취합, 검증 로그 생성, 이메일 초안 작성처럼 산출물이 여러 개 생긴 작업은 세션 종료 또는 인수인계 전에 루트 파일을 정리한다. 정리 목적은 최종 사용 파일과 중간 산출물을 분리하여 다음 작업자가 최종본을 혼동하지 않도록 하는 것이다.

### 11.1 루트에 남길 파일

루트에는 다음 파일만 남기는 것을 원칙으로 한다.

- 최종 제출본 또는 현지조사 당일 바로 사용할 파일
- 원 공문, 기준 양식, 최종 집계표
- `AGENTS.md`, `README.md`, `HANDOFF_SUMMARY.md` 등 작업 지침과 인수인계 파일
- 사용자가 즉시 열 가능성이 높은 진행 중 파일

### 11.2 보존 이동할 파일

검증 메모, 추출 결과, 초안, 중간 버전, 임시 비교자료는 삭제하지 말고 날짜별 산출물 폴더로 이동한다.

권장 구조는 다음과 같다.

```text
작업산출물_YYYYMMDD/
  01_집계검증/
  02_담당자검증/
  03_요청초안/
  04_추출검토/
  cleanup_log_YYYYMMDD.csv
```

업무 성격에 따라 하위 폴더명은 조정할 수 있으나, 같은 세션 안에서는 번호와 명칭을 일관되게 유지한다.

### 11.3 이동 원칙

- 기본은 삭제가 아니라 보존 이동이다.
- 사용자가 명시적으로 삭제를 요청하지 않은 파일은 지우지 않는다.
- 이동 전후 파일 목록을 확인한다.
- 이동 로그에는 원래 경로, 이동 경로, 처리 시각을 남긴다.
- 이동 후 `HANDOFF_SUMMARY.md`의 파일 경로를 실제 위치와 맞춘다.
- 인수인계에 언급된 파일이 보이지 않으면 곧바로 누락으로 단정하지 말고, 사용자가 직접 처리·삭제·대체했는지 확인한다.

### 11.4 인수인계 반영 항목

세션 종료 시 `HANDOFF_SUMMARY.md`에는 최소한 다음을 반영한다.

- 루트에 남긴 최종 파일
- 이동한 산출물 폴더와 주요 파일 위치
- 삭제한 파일이 있는지 여부
- 사용자가 직접 처리하거나 삭제한 자료
- 다음 작업자가 확인해야 할 파일 또는 누락 위험
